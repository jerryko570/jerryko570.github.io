GitHub 블로그에서 흥미로운 글을 봤다. GitHub APAC 마케팅 리드가 반복적인 이벤트 관리 업무를 GitHub Copilot과 Actions로 자동화한 이야기인데, 기술 설명이라기보다 "업무를 문서화할 수 있으면 자동화할 수 있다"는 한 문장이 먼저 눈에 들어왔다.

개발 도구로 마케팅 운영을 자동화했다는 게 처음엔 좀 낯설었다. 보통 GitHub Copilot이라고 하면 코드를 쓰거나 PR을 리뷰하는 이미지가 강한데, 이게 마케팅 이벤트 관리에 쓰인다는 게 신기해서 읽어봤다.

## 1️⃣ 이게 뭐냐?

핵심 개념은 GitHub Copilot Skills다. Markdown 파일로 "이 업무는 이렇게 한다"를 적어두면 Copilot이 그 절차를 읽고 실행해준다. runbook을 쓰듯이 업무 흐름을 글로 정리하면 그게 자동화의 기반이 된다는 발상이다.

실제 흐름을 보면 이렇다. "11월 AI 웨비나를 열고 싶다"는 메시지를 GitHub Copilot에 보내면, AGENTS.md라는 팀 운영 지침을 읽고 캠페인 이름을 제안하고 초대 이메일 초안 두 가지를 작성해준다. 사람이 확인하면 그다음부터는 자동이다. Issue가 생성되고, 붙은 라벨이 GitHub Actions를 트리거해서 랜딩 페이지 복제, UTM 링크 생성, 이메일 문서 작성이 이어진다.

이전에는 이 모든 게 수작업이었다. 랜딩 페이지를 복제하고, UTM 링크를 만들고, 이메일 초안을 요청하고, 등록자 목록을 내려받아 정리하고, 이벤트가 끝나면 CRM에 올리는 것. 이걸 Issue 하나로 시작할 수 있게 된 거다.

자동화 단계는 Pull Request로 검토한 뒤 병합하는 구조다. 코드 리뷰처럼 업무 절차도 버전 관리된다는 점이 흥미로웠다. 누가 어떤 절차를 바꿨는지 추적할 수 있고, 잘못됐을 때 되돌리는 것도 가능하다.

## 2️⃣ 내가 든 생각

"Copilot이 초안을 쓰고, 사람이 결정한다"는 역할 분리가 눈에 들어왔다. AI가 전부 처리하는 게 아니라 제안 → 검토 → 실행 흐름이 명확하게 나눠져 있다. 현실적으로 도입할 수 있는 구조처럼 보였다.

👉🏻 AGENTS.md 개념이 특히 인상적이었다. 팀 운영 방식을 Markdown으로 문서화하면 Copilot이 그걸 읽고 맥락에 맞는 제안을 한다. 결국 "AI에게 컨텍스트를 잘 넘기는 방법"에 대한 이야기인 것 같았다. 잘 쓴 문서가 곧 좋은 자동화의 출발점이 된다는 구조다.

DRY_RUN 모드도 눈에 띄었다. 실제로 실행하기 전에 어떤 일이 벌어질지 미리 확인하는 기능인데, 공부한 내용 기준으로는 망가뜨릴 걱정 없이 연습할 수 있다는 안전장치가 있다는 점이 학습자 입장에서 반갑게 느껴졌다.

> 💡 **여기서 드는 질문?**
> 마케팅 운영에 이게 된다면, 디자인 운영에도 비슷한 흐름을 만들 수 있을까? 컴포넌트 추가 요청이 들어오면 Figma 링크, 스펙 문서, GitHub Issue가 자동으로 이어지는 식으로. 구조 자체는 디자인 시스템 관리에도 맞을 것 같다는 생각이 들었다.

## 3️⃣ 앞으로 어떻게 쓸까?

아직 직접 닿아본 적은 없지만, 글에서 제안한 시작점이 현실적으로 느껴졌다. Issue Form 하나, Label 하나, Actions 하나씩 붙여 나가는 방식이다. 처음부터 전부 자동화하려는 게 아니라, 가장 반복적인 업무 하나를 고르고 거기서 시작하는 것.

공부한 내용 기준으로는, 이 접근이 프론트엔드 작업에도 비슷하게 적용될 수 있을 것 같았다. PR 템플릿, 자동 라벨링, 배포 알림 같은 것들이 사실 같은 구조다.

## ⭐️ 마지막으로, DevTools를 공부하면서 든 생각

공부 끝에 남은 건 "문서를 잘 쓰는 사람이 자동화도 잘 설계한다"는 한 줄짜리 인상이다. 자동화의 진입점이 꼭 코드가 아니어도 된다는 이 발상이, 디자이너가 개발 도구에 접근할 때 생각보다 가까운 자리에 있을 수 있겠다는 생각도 들었다.
