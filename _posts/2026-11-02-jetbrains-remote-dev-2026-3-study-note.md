JetBrains 블로그에서 2026.3 버전 원격 개발 기능 업데이트 글을 읽었다. 제목부터 꽤 직접적이었다 — "원격 머신에서 일하는 게 로컬 프로젝트랑 똑같이 느껴져야 한다." 막연히 좋은 말처럼 들리는데, 그게 구체적으로 뭘 말하는 건지 더 들여다보고 싶어졌다.

원격 개발이라는 게 원래는 준비 과정이 꽤 번거로운 편인 것 같다. SSH 설정도 따로 해야 하고, 세션을 열고 관리하는 것도 IDE 바깥에서 처리해야 하는 경우가 많다는 이야기를 들어왔다. 그 과정에서 생기는 작은 흐름의 단절들이 쌓이면 환경 자체에 에너지를 빼앗기게 되는데 — 이번 업데이트가 그 틈을 메우는 방향인 것 같다.

## 1️⃣ 이번에 뭐가 달라졌나?

문서를 정리해보니 변화가 두 가지로 요약됐다.

첫째, 원격 세션을 IDE 안에서 직접 시작하고 관리할 수 있게 됐다. 이전에는 별도 도구를 거쳐야 했을 것 같은데, 이제는 IDE 안에서 세션을 열고 이어서 작업하는 흐름 자체가 IDE 내부로 들어온 것 같다. "열고, 코딩 시작하고, 이어서"라는 흐름이 하나의 화면 안에서 이어진다는 거다.

둘째, SSH 연결이 native OpenSSH 방식으로 바뀌었다. 이게 꽤 중요한 변화인 것 같다는 생각이 들었다. 이미 쓰고 있는 SSH 키나 설정을 그대로 쓸 수 있다는 뜻이니까. 새로운 연결 방식을 따로 익히는 게 아니라 아는 방식 그대로 연결한다는 점에서 전환 비용이 줄어드는 방향에 가까운 것 같다.

👉🏻 요약하면, "원격이라는 걸 의식하지 않아도 되는 흐름"을 만드는 게 이번 업데이트의 방향인 것 같다.

## 2️⃣ 읽으면서 든 생각

이 업데이트를 정리하면서 "투명한 도구"라는 개념이 떠올랐다. 잘 만들어진 도구일수록 도구 자체가 눈에 안 띄게 된다는 이야기. 원격 개발에서도 같은 방향인 것 같다 — SSH 연결, 세션 관리, 환경 설정이 전부 배경으로 사라지는 것.

디자인할 때도 비슷한 고민을 하는 편이다. 사용자가 앱을 쓰면서 "이게 어떻게 돌아가는 거지"를 생각하는 순간이 UX의 실패 신호인 것처럼, 개발 환경에서도 환경 자체에 주의가 묶이는 순간이 흐름이 끊기는 지점이 된다. 이번 변화는 그 원칙을 IDE에 적용한 버전처럼 읽혔다.

> 💡 **그러면 "로컬처럼 느껴진다"는 기준은 어디서 오는 걸까?**
> 결국 비교 대상인 로컬 개발 경험이 이미 얼마나 잘 정립되어 있느냐에 달린 것 같다. 원격의 UX는 로컬의 UX를 따라가는 방식으로 정의되는 셈이다.

문서의 다른 포인트로 "이전에 하던 작업을 이어서 할 수 있다(pick up where you left off)"는 표현이 있었다. 단순히 연결이 편해진다는 게 아니라, 세션 상태를 기억해서 다시 시작하는 느낌이 아니게 한다는 건데 — 이게 원격 특유의 불연속성을 줄이는 방향인 것 같다. 처음 읽었을 땐 별것 아닌 것처럼 느껴졌는데, 생각해보니 이게 꽤 중요한 차이일 수 있겠다는 생각이 들었다.

## ⭐️ 마지막으로, 도구 관점에서 공부하며 든 생각

공부 끝에 남은 건 "편리함"보다 "전환 비용"이 더 정확한 말이라는 한 줄이다. 원격이든 로컬이든, 환경을 바꾸거나 연결하는 과정에서 생기는 작은 마찰들이 쌓이면 개발자는 코드보다 환경에 먼저 에너지를 쓰게 된다. 이번 업데이트가 노리는 게 그 마찰을 줄이는 것이라는 게 이해됐다.

전체 기능 목록은 원문에서 확인하는 편이 정확할 것 같다.
