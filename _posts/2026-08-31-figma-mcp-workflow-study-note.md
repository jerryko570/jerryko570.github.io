Figma 블로그에서 에이전트와 디자인-코드 워크플로우를 다룬 글을 읽었다. 제목을 보고 스쳐 지나치려다, "코딩 에이전트는 받은 맥락만큼만 좋은 결과를 낸다"는 문장에 눈이 멈췄다. 그 전제 하나로 글 전체 논리가 흘러가는 방식이 흥미로워서 꼼꼼히 읽어봤다.

요즘 AI 코드 에이전트 이야기를 자주 듣는데, 대부분 "스크린샷 주면 코드 만들어줌" 수준에서 끝나는 것 같았다. 이 글은 거기서 한 발 더 나가서, Figma 라이브러리 자체를 에이전트의 context로 연결하면 어떻게 되는지를 다루고 있었다. 디자인과 코드 사이의 불일치가 늘 신경 쓰였는데, 그 문제를 다른 방향에서 보는 글이라 집중해서 읽었다.

## 1️⃣ 이게 뭐냐?

핵심은 **Figma MCP 서버**다. MCP(Model Context Protocol)를 통해 코드 에이전트가 직접 Figma 라이브러리에 접근하도록 연결하는 구조다. 글에서 소개한 도구들:

- `search_design_system`: 라이브러리에서 비슷한 컴포넌트를 자동으로 찾아줌
- `get_variable_defs`: 색상, 간격 같은 설계 변수를 최신 상태로 가져옴
- `use_figma`: 코드로 만든 UI를 다시 Figma 캔버스로 올려서 보정 가능

여기에 **Code Connect**가 함께 쓰인다. 각 컴포넌트를 GitHub 구현 파일과 양방향으로 연결해두면, 에이전트가 이미 구현된 컴포넌트를 파악하고 새로 만들지 않는다. `Button` 컴포넌트를 만들려 할 때, `src/components/Button.tsx`가 연결돼 있으면 그걸 재사용하는 방식이다.

글에 나온 사례는 메시지 대량 관리 UI였다. 툴바, 모달, 토스트 세 화면을 구현하는 과정에서 색상과 모서리 반경이 바뀌자, 에이전트가 설계 변수를 감지하고 코드를 자동으로 업데이트했다.

## 2️⃣ 내가 든 생각

처음에 MCP라는 단어만 봤을 땐, 에이전트가 Figma 파일을 어딘가에서 읽어오는 정도로 이해했다. 근데 실제로 보니 단순히 '읽기'가 아니라, 컴포넌트 변수 상태를 실시간으로 추적하고 코드와 동기화하는 구조에 가까웠다. 에이전트가 스크린샷이 아니라 살아있는 라이브러리를 본다는 차이가 꽤 컸다.

👉🏻 디자이너 입장에서 가장 눈에 들어온 건 `get_variable_defs`였다. 색상이나 간격을 하드코딩하면 디자인이 바뀔 때마다 코드를 손으로 수정해야 하는데, 설계 변수를 기준으로 그 차이를 자동으로 잡아준다는 게 꽤 달랐다. 에이전트 시대에도 디자인 시스템을 꼼꼼하게 정리해야 하는 이유가 하나 더 생긴 것 같다는 생각이 들었다.

`use_figma`도 흥미로웠다. 코드로 만든 컴포넌트를 다시 Figma 캔버스로 올려서 보정한다는 게, 기존의 "디자인 → 코드" 단방향 흐름과는 다른 모양이었다. 디자이너로서 그동안 핸드오프라는 단어가 항상 단절처럼 느껴졌는데, 이 구조는 그 단절을 다른 방식으로 메우려는 시도처럼 보였다.

> 💡 **여기서 드는 질문?**
> Code Connect로 컴포넌트와 코드 파일을 연결하는 작업은 누가 담당하는 걸까? 디자이너 몫인지, 개발자 몫인지, 문서만 봐서는 아직 모르겠다.

## ⭐️ 마지막으로, 디자인 도구 공부하며 느낀 점

정리해보니 이건 에이전트 도구 이야기라기보다, 디자인 시스템을 얼마나 잘 쌓아뒀냐는 이야기에 가까웠다. 에이전트한테 스크린샷 대신 라이브러리를 보게 하려면, 그 라이브러리 안에 정보가 먼저 잘 정리돼 있어야 한다. 도구가 바뀌어도 기초가 중요하다는 건 크게 다르지 않은 것 같다.
