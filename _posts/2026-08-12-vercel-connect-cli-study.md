Vercel 공식 블로그에서 Connect CLI 업데이트 발표가 있었다. 이전까지 `vercel connect create` 명령어를 실행하면 일부 서비스는 터미널에서 설정이 끝났고, 나머지는 대시보드 창이 자동으로 열리는 식이었다. 이번 업데이트로 그 범위가 100개 이상의 서비스로 넓어졌다는 내용이었다.

읽다 보니 `getToken`이라는 API 구조가 눈에 들어왔다. 단기 토큰(short-lived, scoped token)을 요청하는 방식인데, 자격 증명을 코드와 분리하는 구조가 흥미로워서 조금 더 들여다봤다.

## 1️⃣ 이게 뭐냐?

Vercel Connect는 외부 서비스를 Vercel 프로젝트에 연결하는 기능이다. DB, 인증 서비스, 서드파티 API 같은 것들을 커넥터 단위로 묶어서 관리한다.

이번 업데이트 전까지는 CLI 지원이 들쭉날쭉했다. `vercel connect create`를 실행하면 어떤 서비스는 터미널 안에서 모든 게 끝났고, 어떤 서비스는 대시보드 창이 열렸다. 이번에 그 경계가 없어지고 100개 이상의 서비스를 CLI 안에서 처리할 수 있게 됐다.

커넥터를 만드는 흐름은 이렇다. CLI에서 서비스 이름을 넘기면 브랜드명, 아이콘, 인증 방식이 자동으로 채워진다. 필요한 자격 증명만 입력하면 커넥터가 생성된다. 이후 `vercel connect attach`로 프로젝트와 배포 환경을 지정해서 붙인다.

코드에서 서비스를 사용할 때는 `getToken`에 커넥터 고유식별자(`service/name`)를 넘긴다. 그러면 Vercel이 단기 토큰을 돌려준다. 이 토큰은 만료 시간이 짧고, 해당 커넥터 권한으로만 범위가 제한(scoped)되어 있다고 문서에 나와 있었다.

## 2️⃣ 내가 든 생각

처음엔 "CLI 지원 서비스 수가 늘었구나" 정도로 읽었다. 근데 `getToken` 구조를 보고 나서 생각이 조금 달라졌다.

API 키를 코드 안에 직접 두는 방식이 아니라, 커넥터가 중간에 앉아서 그때그때 토큰을 발급하는 구조다. 권한이 커넥터 단위로 묶여 있으니, 특정 커넥터가 문제가 생겨도 다른 서비스 자격 증명으로 번지지 않는 형태다.

👉🏻 이 구조에서 흥미로웠던 건, Vercel이 단순한 배포 플랫폼이 아니라 서비스 간 인증 흐름의 중간 지점에 서 있다는 느낌이었다. 연결을 추상화하면서 그 경계에서 보안도 같이 가져가는 모양새인 것 같다.

> 💡 **그럼 이 토큰은 실제로 어디서 만료 처리가 되는 걸까? Vercel 서버인가, 아니면 연결한 서비스 쪽인가?**

디자이너 관점에서 보면, CLI로 흐름이 통일된다는 게 컨텍스트 스위칭 문제를 해결하는 것처럼 보였다. 설정 도중 대시보드가 열리는 순간 흐름이 끊긴다. 터미널 안에서 모든 게 해결된다면 그 흐름이 유지된다. 사소해 보이지만, 이런 흐름 유지가 얼마나 중요한지는 디자이너 관점에서 더 공감이 가는 부분이었다.

## ⭐️ 마지막으로, 연결이라는 일을 공부하며 든 생각

이런 류의 도구를 볼 때 자꾸 같은 질문을 하게 되는 것 같다 — "이게 편의를 위한 건가, 아니면 통제를 위한 건가." Connect CLI 업데이트도 처음엔 편의 기능으로 읽혔는데, `getToken` 구조를 보고 나서는 그 경계가 좀 흐릿해졌다. 편의와 통제가 하나의 설계 안에 같이 있는 경우가 꽤 된다는 인상이었다.
