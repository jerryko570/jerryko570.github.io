토스 블로그에서 LLM 비용 관련 글이 올라왔다. 제목이 "손가락 튕기기"여서 처음엔 좀 가볍게 읽을 생각이었는데, 읽고 보니 생각보다 구조가 잘 잡혀 있었다.

SNAP(Selective Native AI Processing)이라는 이름이다. 모든 LLM 호출을 한꺼번에 작은 모델로 교체하는 게 아니라, 내재화 모델이 자신 있을 때만 처리하고 나머지는 기존 LLM에 넘기는 방식이다. 이 분기 구조가 어떻게 돌아가는지 궁금해서 좀 더 파봤다.

## 1️⃣ 이게 뭐냐?

핵심은 Confidence 기반 분기다. 내재화 모델이 요청을 처리하면서 자신감 점수를 내보내고, 그 점수가 임계값 이상이면 결과를 쓰고 아니면 원래 LLM으로 넘긴다.

이때 Task Fingerprint라는 개념이 작업 분류를 담당한다. System Prompt의 앞부분, Role과 작업 정의 부분을 해시해서 작업 단위를 구분하는 방식이다. Few-shot 예시가 자주 바뀌어도 앞부분은 대체로 유지되니까, 이걸로 "어떤 종류의 작업인가"를 안정적으로 잡을 수 있다는 거다.

매일 배치 파이프라인이 돌면서, 이 Fingerprint 기준으로 호출량 많고 비용 높은 작업들을 자동으로 후보로 추린다. 거기서 응답이 정형화돼 있고 학습 데이터가 충분한 것들만 내재화 학습으로 이어진다. 전체를 한꺼번에 바꾸는 게 아니라, 최적화 가능한 구간부터 자동으로 찾아가는 구조라고 보면 될 것 같다.

## 2️⃣ 내가 든 생각

처음엔 Confidence 점수가 정확도랑 같은 거라고 생각했는데 아니었다. 점수가 높아도 그 숫자 그대로 정확도를 보장하는 게 아니고, 검증 데이터로 실제 일치율을 따로 측정해서 임계값을 골라야 한다. 이 부분이 이해하는 데 시간이 좀 걸렸다.

그래서 접근 방식이 이렇다. 먼저 목표 일치율을 정하고, 그 조건에서 커버리지가 가장 넓어지는 임계값을 찾는다. 목표를 높이면 커버리지가 줄고, 낮추면 늘어난다. 이 트레이드오프가 파라미터 하나로 조절된다는 게 꽤 깔끔하게 느껴졌다.

👉🏻 이 Fallback 구조를 보면서 UI의 Graceful Degradation이 떠올랐다. 확신이 낮으면 다른 경로로 넘기는 것, 시스템이 스스로 한계를 감지하고 처리를 위임하는 방식. AI 응답 설계에서도 이런 분기를 의도적으로 만들 수 있다는 게 처음 생각해본 부분이었다.

> 💡 **여기서 드는 질문?**
> Task Fingerprint가 System Prompt 앞부분에 의존한다면, 프롬프트 구조를 팀마다 다르게 쓰거나 자주 바꾸면 분류가 흔들리지 않을까? 그러면 프롬프트 템플릿을 팀 공용 자산으로 안정적으로 관리하는 게 선행 조건이 되는 것 같다.

## 3️⃣ 앞으로 어떻게 쓸까?

아직 직접 닿아볼 단계는 아니지만, 개념 자체는 머릿속에 남아있다. "자신 있는 케이스만 처리하고, 모호한 건 다른 경로로 넘긴다"는 방식은 AI 기반 UI 판단이나 추천 시스템에서도 비슷한 형태로 나오는 것 같다. Confidence를 기준으로 자동 처리와 그렇지 않은 처리를 구분하는 판단, 앞으로 다른 곳에서도 이 패턴이 눈에 들어올 것 같다.

## ⭐️ 마지막으로, 구조 설계 관점에서 공부하며 든 생각

정리해보니 이건 비용 절감 이야기라기보다 "어떤 요청은 자신 있게 처리하고 어떤 건 못 하는지를 자동으로 발견하는 방법" 이야기에 가까웠다. 공부 끝에 남은 건 하나 — 시스템이 스스로 자기 한계를 찾아가게 만든다는 인상이다.
