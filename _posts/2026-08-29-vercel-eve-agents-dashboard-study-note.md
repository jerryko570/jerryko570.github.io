Vercel 블로그에 대시보드에서 AI 에이전트를 직접 만들고 배포할 수 있다는 기능이 올라왔다. "eve agents"라는 이름인데, 처음엔 그냥 또 다른 챗봇 빌더겠지 싶었다. 이미 비슷한 게 너무 많기도 하고.

근데 조금 읽어보니 빌더 자체의 설계 방식이 흥미로웠다. 공부한 내용을 정리해봤다.

## 1️⃣ 이게 뭐냐?

Vercel 대시보드 안에서 에이전트를 만들 수 있는 빌더가 생겼다. "Add New → Agent"를 선택하면 빌더가 열리고, 거기서 몇 가지를 정하면 된다.

에이전트의 동작 방식을 정의하는 **instructions**를 텍스트로 쓰고, 어떤 모델을 쓸지 고른다. 이 모델 선택이 특이한 부분인데, AI Gateway를 통해 다양한 모델을 선택할 수 있는 구조다. 인터페이스는 Next.js 웹 채팅이나 Slack 채널 중 하나를 고르는 식이고, Linear나 Notion 같은 서비스를 built-in 연결로 붙이거나 커스텀 MCP 서버를 직접 연결할 수도 있다.

빌더가 내부에서 하는 일은 꽤 많다. 설정을 마치면 코드가 담긴 private Git 저장소를 자동으로 생성하고, 그걸 Vercel 프로젝트로 배포까지 마친다. 설정이 끝나는 순간 바로 대화할 수 있는 에이전트가 올라온 상태가 된다.

결국 사용자가 직접 결정하는 건 두 가지 정도인 것 같다. "이 에이전트는 무슨 일을 하는가"(instructions)와 "어디서 쓸 건가"(채널). 저장소 구조나 배포 파이프라인, 도구 연결 방식은 플랫폼이 처리한다.

## 2️⃣ 내가 든 생각

디자이너 시선에서 보면 이 빌더의 UX 결정이 흥미롭다. 복잡한 것들을 다 감추고, 사용자 앞에 내놓는 건 instructions 텍스트 하나다. 코드를 전혀 안 봐도 에이전트를 만들 수 있는 구조인데, 그렇다고 "노코드"라는 말이 어울리지도 않는다. instructions를 잘 쓰는 것 자체가 에이전트 품질을 좌우하니까, 오히려 더 언어적인 작업에 가까운 것 같다.

👉🏻 "AI Gateway에서 아무 모델이나 선택 가능"이라는 부분이 제일 눈에 들어왔다. 같은 instructions를 두고 모델만 바꿔서 결과가 어떻게 달라지는지 확인해볼 수 있는 구조라, 에이전트 설계를 실험적으로 접근하기 좋겠다는 생각이 들었다.

MCP 연결도 두 방향으로 나뉘어 있다. Linear나 Notion 같은 서비스는 built-in 연결로 바로 붙일 수 있고, 그 외에는 커스텀 MCP 서버를 직접 연결하는 방식이다. 문서만 본 입장에서는 어디까지 확장이 되는지 잘 가늠이 안 됐다.

> 💡 **여기서 드는 질문?**
> instructions를 잘 쓰는 것과 프롬프트 엔지니어링은 같은 스킬일까? 에이전트가 도구를 쓰는 맥락에서는 접근 방식이 달라지는 걸까?

## ⭐️ 마지막으로, 빌더 설계를 공부하며 든 생각

정리해보니 이 빌더에서 흥미로운 건 에이전트 생성 흐름 자체보다, 빌더가 어떤 것을 드러내고 어떤 걸 감췄는지에 있었다. 코드도 배포 설정도 다 숨겼는데 instructions는 텍스트 그대로 노출한 건, 하나의 관점처럼 읽혔다 — 에이전트의 핵심은 코드가 아니라 지시문에 있다는.
