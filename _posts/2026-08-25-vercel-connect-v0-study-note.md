Vercel 체인지로그에서 흥미로운 발표를 읽었다. v0로 만든 앱을 Slack, Google, Notion, GitHub, Salesforce 같은 서비스와 연결할 수 있게 됐다는 내용이었다. Vercel Connect라는 이름인데, 처음엔 API 연동이 조금 쉬워지는 정도겠거니 생각했다. 근데 조금 더 읽어보니 연결이 되는 구조 자체가 달랐다.

특히 눈에 들어왔던 건 "연결이 된다"는 결과보다, 어떤 방식으로 동작하느냐였다. 그 부분이 궁금해서 더 파고들어봤다.

## 1️⃣ 이게 뭐냐?

v0 안에서 "이 앱을 Slack에 연결해줘"라고 입력하면, v0가 커넥터 설정을 열고 직접 안내해준다. 설정이 끝나면 팀 단위로 저장되어서, 같은 팀에서 다른 앱을 만들 때 같은 서비스를 다시 설정할 필요가 없다.

연결 가능한 서비스는 크게 두 종류로 나뉜다. Slack, GitHub 같은 서비스는 "managed connector"로 분류된다. Vercel이 앱 등록을 대신 처리해주는 방식이라, OAuth 앱을 직접 만들거나 API 키를 별도로 발급받을 필요가 없다. 다른 서비스는 직접 credential을 입력하면 된다.

토큰 발급 방식도 특이했다. 앱이 서비스에 접근할 때 Vercel이 런타임에 short-lived token을 발급한다. 앱 코드나 환경 변수에 장기 API 키를 보관하지 않아도 되는 구조다. 필요할 때만 토큰이 발급되고, 금방 만료되는 방식이다.

발표에서 든 예시도 인상적이었다. 음성으로 브라우저를 조작하는 에이전트를 v0에서 만든 케이스가 있었고, Slack, Gmail, Linear 데이터를 한 화면에 모아 요약해주는 대시보드도 이 방식으로 구현했다고 한다. 프로토타입을 넘어서 실제 데이터가 붙은 앱을 v0에서 만들 수 있다는 게 이런 형태로 구체화된 셈이었다.

## 2️⃣ 내가 든 생각

v0를 볼 때 항상 마음 한켠에 걸렸던 게 있었다. "UI는 금방 나오는데, 실제 데이터는 어떻게 붙이지?"였다. 프로토타입 수준은 빠르게 나오는데, 실제 서비스와 연결하려면 결국 코드를 건드려야 하는 단계가 있다는 점이 아쉬웠다. Vercel Connect가 그 간격을 좁히려는 시도처럼 읽혔다.

디자이너 입장에서 목업과 실제 데이터 사이의 간격은 꽤 크다. 텍스트 자리에 실제 Slack 메시지나 Gmail 내용이 들어왔을 때 레이아웃이 어떻게 보이는지는 정적인 프로토타입만으로는 알기 어렵다. 실데이터가 붙는 순간 디자인이 달라 보이는 경우가 많다. 그 부분에서 Vercel Connect가 의미 있는 변화를 만들 수 있을 것 같다는 인상이었다.

short-lived token 구조는 공부하면서 조금 더 와닿았다. 장기 키를 어딘가에 보관하면 관리 포인트가 늘어나고, 유출됐을 때 피해 범위도 커진다. 런타임에 필요할 때만 토큰이 나오는 방식이 왜 더 안전한지 — 개념은 알고 있었는데, 이런 형태로 구체화된 사례를 보니 좀 더 연결되는 느낌이었다.

👉🏻 팀 단위 커넥터 구조도 재미있게 읽었다. 한 번 설정해두면 팀 전체가 재사용할 수 있다는 게, 디자이너 입장에서는 협업 구조 얘기로 이어진다. 어떤 서비스를 팀 레벨에서 공유하고 누가 관리하느냐 — 도구 설계가 조금씩 협업 방식을 바꾸는 것 같다.

> 💡 **여기서 드는 질문?**
> managed connector가 "Vercel이 앱 등록을 대신 처리해준다"는 건 편한데, 그러면 내부적으로 어떤 범위의 권한이 Vercel에게 위임되는 건지 — 공부한 내용 기준으로는 이 경계를 명확히 이해하고 쓰는 게 중요할 것 같다.

## ⭐️ 마지막으로, v0를 공부하면서 드는 생각

이런 류의 연결 도구를 볼 때마다 자꾸 같은 질문을 하게 된다 — 복잡한 설정을 추상화해주는 게 편의인가, 아니면 내가 모르는 사이에 어딘가를 위임하고 있는 건 아닌가.
