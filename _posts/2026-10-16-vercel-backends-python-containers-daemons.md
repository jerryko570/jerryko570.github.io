Vercel 공식 블로그에서 백엔드 확장 관련 발표가 있었다. Ship 2026 이벤트 정리 글에서 먼저 봤고, 별도 포스트로 자세한 내용이 올라와서 읽어봤다. 프론트엔드 공부를 하면서 Vercel을 자주 보게 되는데, 이번 건 좀 읽어둘 만하다 싶었다.

핵심은 세 가지다. Python 정식 출시, 컨테이너 지원 확대, 그리고 Daemons 퍼블릭 베타.

## 1️⃣ 이게 뭐냐?

**Python GA**는 FastAPI, Flask, Django 같은 Python 백엔드 프레임워크를 Vercel에 직접 올릴 수 있게 됐다는 내용이다. 표준 CPython 위에서 실행되고, PyPI 의존성이나 `uv` 기반 프로젝트도 그냥 된다. 프레임워크 자동 감지에 빌드와 스케일링까지 Vercel이 맡는다는 게 요점이다. 이전까지도 어느 정도 가능했지만, 이번에 정식 지원으로 전환된 것 같다.

**컨테이너 지원**은 Dockerfile로 패키징한 앱을 그대로 올리는 기능이다. Go, Rust, 또는 `ffmpeg` 같은 시스템 라이브러리가 필요한 작업도 가능해진다고 한다. Fluid compute 위에서 실행돼서 실제로 요청을 처리하는 시간에만 과금된다는 설명이 있었다. CDN, WAF, 로그, 롤백도 그대로 쓸 수 있다고.

**Daemons**는 여기서 처음 보는 개념이었다. 상시 실행되는 백그라운드 워커를 컨테이너로 배포하는 기능이고, 현재는 퍼블릭 베타 단계다. 큐에서 메시지를 폴링하거나, DB에 쌓인 작업을 가져오는 pull 방식 워크로드에 적합하다고 한다. 리전별로 인스턴스 수를 지정해두면, 프로세스가 죽었을 때 Vercel이 자동으로 재시작해준다.

## 2️⃣ 내가 든 생각

지금까지 Vercel은 Next.js 올리는 곳 정도로 생각해왔다. 이번 발표를 읽으면서 그 인식이 조금 달라졌다.

👉🏻 흥미로웠던 건 프론트엔드와 백엔드가 같은 프로젝트 안에서 배포되는 구조였다. Next.js 프론트와 FastAPI 백엔드를 하나의 저장소에 두고, PR 하나를 올리면 preview URL이 둘 다 담긴 형태로 나온다는 방식. 서비스를 따로 올리고 URL을 따로 맞추는 방식과 비교하면 개발 흐름이 꽤 달라질 것 같다는 생각이 들었다.

Daemon은 개념 자체가 낯설었다. "서버리스 플랫폼인데 상시 실행 프로세스가 있다는 게 맞나?" 싶었다. 문서를 읽어보니 완전한 서버리스라기보다는 관리형 백그라운드 워커에 가까운 것 같다. 서버처럼 계속 켜져 있되, 컨테이너 관리와 재시작은 플랫폼이 맡는 방식이라는 게 내가 이해한 내용이다.

> 💡 **여기서 드는 질문**  
> Daemon을 리전에 하나 올려두면 그게 계속 실행되고 있는 건데, 비용이 서버리스처럼 처리 시간 기준인지, 서버처럼 실행 시간 전체를 과금하는지가 가장 궁금했다. 문서에서는 명확하게 찾지 못했다.

## 3️⃣ 디자이너 입장에서 보면

Python이 GA가 됐다는 게 UI 개발 맥락에서도 조금 흥미롭게 읽혔다. Figma 플러그인이나 프로토타입에 간단한 AI 기능을 붙이는 작업을 할 때, 백엔드가 잠깐 필요한 경우가 있다. 그럴 때 Next.js API route로 어떻게든 버티거나, 별도 서버를 열거나 했는데, 공부한 내용 기준으로는 Python 백엔드가 같은 프로젝트 안에 들어가는 구조가 그 선택지를 하나 더 만들어주는 것 같다.

아직 직접 닿아본 적은 없어서 실제로 어떤 방식으로 쓰는 게 좋은지는 모르겠다. 문서만 본 입장에서는 그런 방향이 보인다는 정도다.

## ⭐️ 마지막으로

공부 끝에 남은 건 "Vercel이 프론트엔드 플랫폼에서 풀스택 배포 플랫폼으로 가고 있다"는 한 줄이다. 에이전트 인프라 얘기도 많이 나오고, 이번에 백엔드 지원 폭도 넓어졌다. "Next.js 올리는 곳"으로만 봐왔던 것과 실제로 하고 있는 것 사이에 꽤 차이가 생긴 것 같다.
