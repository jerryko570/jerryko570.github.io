토스 Tech 블로그에서 App Router 관련 글을 읽었다. 제목부터가 물음표였다. "App Router의 장점은 우리에게도 장점일까요?" 보통 기술 도입 글은 "왜 썼는가"를 다루는데, 이 글은 "직접 측정했고, 도입하지 않기로 결정했다"는 흐름이었다.

프론트엔드를 공부하다 보면 새 기술이 나올 때마다 막연하게 "써야 할 방향 아닐까"라는 생각이 든다. App Router도 그중 하나였는데, 이 글이 그 질문을 다르게 보게 했다.

## 1️⃣ 이게 뭐냐?

App Router는 Next.js 13 이후 기본이 된 라우팅 방식이다. React Server Components(RSC)를 기반으로 하고, Suspense 기반 스트리밍과 서버에서 직접 인증 정보에 접근할 수 있는 `headers()` API 같은 기능이 들어왔다.

토스뱅크 팀이 집중해서 본 건 세 가지였다. RSC로 번들 크기 줄이기, 스트리밍으로 준비된 영역 먼저 보여주기, 서버 환경에서의 인증 처리. 문서만 보면 다 좋아 보였는데, 실제 환경에서 직접 확인하면서 상황이 달라졌다.

스트리밍 결과가 예상과 달랐다. 서비스가 세로 스택 구조의 웹뷰 환경에서 돌아가다 보니, WebKit이 마지막 섹션이 준비될 때까지 렌더링을 미뤘다. "준비된 것부터 먼저 보여준다"는 장점이 실제 환경에서는 레이아웃이 튀는 문제로 이어졌고, 스켈레톤 높이를 일일이 관리해야 하는 부담도 생겼다.

## 2️⃣ 내가 든 생각

👉🏻 "많이 쓰인다"와 "우리한테 맞다"가 다르다는 걸 이 글에서 제일 명확하게 봤다.

RSC는 좀 달랐다. 번들 크기 감소가 실제로 측정됐고, 패키지의 `"react-server"` 조건부 export를 통해 서버/클라이언트 환경별 코드를 분리하는 방식도 개발 흐름에 실질적으로 도움이 됐다고 했다. 나도 왜 RSC를 써야 하는지 막연했는데, 패키지 단위에서 환경별로 다른 코드를 실행한다는 구체적인 그림이 생겼다.

> 💡 **여기서 드는 질문** — 경계를 나누는 게 좋다는 건 알겠는데, 잘못 그었을 때 비용은?

글이 이 부분도 다뤘다. 앱 브릿지 같은 의존성이 서버 환경에서 조용히 실패하거나, 캐시 키에 사용자 정보가 빠지면 엉뚱한 응답이 나가는 위험. 나눴는데 오히려 새 위험이 생기는 상황이었다. Pages Router와 App Router를 병행하면 안전해 보이지만, `basePath` 설정 충돌이나 경로가 중복으로 붙는 문제가 실제로 발생했다고 했다. 점진적 마이그레이션이 충돌 지점을 늘린 셈이었다.

디자이너로서 보면, 경계를 잘못 그었을 때 조용히 실패하는 구조가 특히 불안하게 느껴졌다. 화면 단에서는 괜찮아 보이는데 뒤에서 무언가 잘못되고 있는 상황.

## ⭐️ 마지막으로

이 글에서 가장 인상적이었던 건 판단 과정을 구체적으로 공개했다는 점이었다. 장점 목록을 나열하고 끝낸 게 아니라, 각 장점이 실제 조건에서 어떻게 작동하는지 확인했고, 비용이 이득보다 크다고 판단해서 도입하지 않았다. 그 과정이 문서로 남아 있다는 게 공부하는 입장에서는 꽤 선명한 예시였다.

공부 끝에 남은 건 "어떤 기술이 좋은가"보다 "내 조건에서 어떻게 작동하는가"가 먼저라는 한 줄이다.
