GitHub 블로그에서 LLM 평가 관련 글을 읽었다. 시크릿 스캐닝 기능에 LLM을 실제로 적용하면서 배운 것들을 정리한 글이었는데, 제목은 "How to evaluate LLMs before production"이었다.

처음엔 모델 선택이나 프롬프트 튜닝 방법론 얘기겠거니 했는데, 읽다 보니 방향이 조금 달랐다. 핵심은 벤치마크 점수가 좋다고 해서 프로덕션에서도 잘 동작하는 건 아니라는 전제에서 출발했고, 그 간극을 어떻게 측정하고 줄이느냐에 대한 이야기였다.

## 1️⃣ 이게 뭐냐?

글에서 소개한 접근 방식은 크게 세 가지 흐름으로 정리할 수 있었다.

첫째, 모델을 조정하기 전에 제품 목표를 먼저 정의한다. 정밀도와 재현율 중 어디에 더 가중치를 둘지, 어떤 실패를 얼마나 허용할 수 있는지를 먼저 합의하지 않으면 평가 숫자가 올라도 그게 의미 있는 개선인지 알 수 없다.

둘째, 오프라인 평가를 코드의 회귀 테스트처럼 다룬다. 프롬프트나 모델이 바뀔 때마다 다시 평가하고, 변수를 하나씩 바꾸면서 비교한다. 평가 결과도 버전 관리를 하면 어떤 변화가 어떤 결과에 영향을 줬는지 나중에 추적할 수 있다.

셋째, 평가 환경을 프로덕션과 최대한 가깝게 유지한다. 깔끔하게 정제된 테스트 케이스만으로는 부족하고, 실제 데이터에 있는 노이즈와 맥락을 포함해야 신뢰도가 올라간다. 레이블(정답 데이터)도 절대적 진실로 보지 않는다. 실제 운영 데이터에는 애매한 케이스가 많기 때문에, 모호함 자체를 인정한 채로 평가를 설계한다.

오류 분석 얘기도 나왔다. 집계 숫자가 개선됐다고 끝내는 게 아니라, 실패가 어떤 패턴인지 — 모델 문제인지, 프롬프트 문제인지, 입력 데이터 문제인지 — 구분해야 다음에 뭘 고쳐야 하는지 방향이 잡힌다. LLM-as-Judge 방식도 소개됐는데, 모든 케이스를 사람이 검토하기 어려울 때 다른 LLM이 1차로 걸러주고 애매한 것만 인간이 보는 방식이었다.

## 2️⃣ 내가 든 생각

디자인에서 "사용자 목표를 먼저 정의한다"는 건 익숙한 원칙인데, LLM 평가에서도 비슷한 논리가 나온다는 게 흥미로웠다. 모델을 먼저 고르는 게 아니라 "이 기능에서 어떤 실패를 얼마나 허용할 수 있는가"를 먼저 정한다는 거니까.

👉🏻 레이블을 신호로 본다는 관점이 특히 남았다. 정답이 항상 명확하지 않다는 걸 인정하면서 평가를 설계한다는 건, 모호함을 없애는 게 아니라 측정 가능한 형태로 다루는 방식에 가까웠다.

오류를 모델/프롬프트/입력으로 나눠 분류한다는 부분도 인상적이었다. 문제의 원인을 명확히 하지 않으면 어디서부터 고쳐야 할지 흐려진다는 건, 디자인 피드백을 정리할 때와 비슷한 것 같기도 했다.

> 💡 **여기서 드는 질문?** 오프라인 평가를 아무리 잘 해도 프로덕션에서 달라지는 이유가 결국 뭘까. 실제 사용 맥락에서만 나타나는 케이스가 평가 셋에 빠진 거라는 설명인데, 그 간극을 완전히 없애는 게 목표인지, 아니면 최소화하는 게 현실적인 목표인지 아직 잘 모르겠다.

## ⭐️ 마지막으로, 개발을 배우는 입장에서 공부하며 남은 것

공부 끝에 남은 건 "평가도 제품 결정의 연장이다"라는 인상 하나다. 좋은 숫자를 내는 게 목표가 아니라, 어떤 상황에서 어떤 실패를 허용할 수 있는지를 먼저 정하고 그 기준으로 모델을 평가한다는 거다. 디자인에서 "완벽한 UI"보다 "이 맥락에서 충분히 좋은 UI"를 정의하는 것과 비슷한 느낌이었다.
