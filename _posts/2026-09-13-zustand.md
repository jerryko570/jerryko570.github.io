## 이 글의 목표

개인 커머스 서비스를 빠르게 만들어 보려고 바이브 코딩으로 붙여나가다 보니, 코드는 돌아가는데 정작 "왜 돌아가는지" 는 모르는 순간이 왔다.
그래서 "장바구니 담기" 버튼 하나를 골라 **클릭 → 저장까지 전 구간**을 끊지 않고 따라가 봤다.

특히 **Zustand + Persist(localStorage)** 로 담은 장바구니가 새로고침해도 안 사라지는 이유를 더 깊이 있게 파고 들어봤다.

---

## 0. 지도부터: 데이터는 이 순서로 흐른다

세부로 들어가기 전에 큰 그림 한 장. **어디까지 서버로 가고, 어디부터 브라우저 안에서만 도는지**가 핵심이다.
![담기 버튼 클릭 하나가 Supabase(원본 창고)에서 React Query 읽기를 거쳐 Zustand 스토어의 set·items 배열에 담기고, persist로 localStorage에 자동 백업되는 전체 데이터 흐름 다이어그램](/assets/img/zustand/zustand-data-flow.jpg){: width="720" }
_클릭 → 저장까지 한 장으로. 아래는 같은 흐름을 텍스트로 다시 짚은 것._

```
━━━ 서버 영역 (여기서만 서버에 감) ━━━
① Supabase  products 테이블              👈🏻 상품 원본 창고
      │
      │  useProduct() = React Query로 조회 (.single)
      ▼
② product = { id, name, price_krw, ... } 👈🏻 상품 한 행(객체)

━━━ 여기부터는 브라우저 안에서만 일어남 ━━━
      │  🖱️ 담기 클릭 → handleAddToCart
      ▼
③ addItem({ 필요한 필드만 })             👈🏻 개발자가(page) 인자를 넣음
      │
      ▼
④ set((state) => ...)                    👈🏻 zustand가 state를 넣음
      │   있으면 수량 +1 / 없으면 새로 추가
      ▼
⑤ items 배열에 저장
      │
      ▼
💾 persist에서 localStorage 자동 백업       👈🏻 새로고침해도 유지 (middleware)
```

**한 줄 요약**

- **읽기(①→②)** = 서버로 감 (React Query)
- **담기(③→⑤)** = 로컬에만 있음 (Zustand + localStorage), 서버 안 감
- 서버로 다시 가는 건 **결제할 때** 뿐

장바구니는 "임시 상태"라 브라우저에만 사는 게 정상이다. 이 경계선을 긋는 게 설계의 핵심인 듯.

## 1. 흐름 따라가기

### A. 데이터를 화면에 가져오기 (읽기: 서버 → 화면)

상품 데이터는 Supabase에서 오고, React Query가 가져온다.

```ts
export const useProduct = (slug: string) =>
  useQuery({
    queryKey: ['product', slug],    // 캐시 이름표 (PK 아님)
    queryFn: async () => {
      const { data } = await supabase
        .from('products')
        .select('*')          // 모든 컬럼
        .eq('slug', slug)     // 이 slug이고
        .eq('is_active', true)// 공개된 것만
        .single()             // 배열 말고 객체 하나로
      return data as Product
    },
  })
```

포인트 두 개만:

- **`.single()`** → 결과를 배열이 아니라 **객체 하나로** 준다. 덕분에 `product[0].id`가 아니라 `product.id`로 바로 쓴다.
- **`return data`** 한 값이 → `useQuery`의 `.data`가 되고 → 컴포넌트에서 꺼낸다.

```ts
const { data: product } = useProduct(slug)
//            └─ data를 product로 rename (왼쪽=원래 이름, 오른쪽=내가 쓸 이름)
```

`product`는 테이블의 **한 행**, `product.id`는 그 행의 **id 컬럼값**이다.
변수 이름(`product`)은 자유지만, 속성 이름(`.id`)은 **컬럼과 일치**해야 꺼내진다.

### B. 장바구니에 담기 (쓰기: 화면 → 로컬)

담기 버튼을 누르면 수량만큼 `addItem`이 호출된다.

```ts
// page (호출) — 빈 상자를 채워서 넘김
addItem({
  id: product.id,
  name: product.name,
  price_krw: product.price_krw,
  // ... 필요한 필드만
})
```

```ts
// cartStore (정의) — 넘어온 값을 받아 상태를 바꿈
addItem: (item) =>
  set((state) => {
    const found = state.items.find((i) => i.id === item.id)
    // 있으면 수량 +1 / 없으면 새로 추가
    ...
  })
```

여기서 `set`은 zustand가 준 **"상태 바꾸는 리모컨"** 이다. 그리고 `set`이 끝나면 뒤에서 `persist`가 `localStorage`에 자동 백업한다.

## 3. 여기서 막혔다면: 꼭 짚고 갈 3가지

흐름을 따라가다 헷갈리는 지점은 거의 이 셋이다. 한 번 잡으면 다른 코드에서도 계속 써먹는다.

### 3-1. 인자 vs 매개변수

```ts
addItem: (item) => { ... }   // 정의: "item"이라는 빈 상자를 만듦  → 매개변수
addItem({ id, name, ... })   // 호출: 그 상자를 값으로 채움        → 인자
```

- **매개변수** = 정의할 때 만든 "이름표 붙은 빈 상자"
- **인자** = 부를 때 그 상자를 채우는 값
- **판단법**: 괄호 `()` 안에 있으면 인자(들어감), `return` 뒤나 `const x =`의 왼쪽이면 리턴(나옴)

`add(3, 4)`에서 `3`이 `a`로 가는 것과 똑같다. `addItem({...})`의 `{}`가 `item`으로 간다.

### 3-2. 콜백: "부르는 쪽이 인자를 채운다"

규칙 하나만 기억하면 된다. **그 함수를 누가 부르냐 = 누가 인자를 채우냐.**

```ts
addItem: (item) => set((state) => { ... })
          └─┬─┘         └──┬──┘
        page가 넣음    zustand가 넣음
```

- `addItem`은 **내가(page)** 부르니까 내가 `item`을 넣는다.
- `set(콜백)`의 콜백은 **zustand가** 부르니까 zustand가 `state`(현재 상태)를 넣는다.

내가 함수를 남한테 넘기면, 받은 쪽이 실행하며 매개변수를 채워준다 — 이게 **콜백 패턴**이고, 사방에 있다.

```ts
array.map((item) => ...)     // map이 item을
array.find((i) => ...)       // find가 i를
set((state) => ...)          // zustand가 state를
onClick={(e) => ...}         // React가 event를
```

라이브러리가 귀찮은 일(반복·상태 꺼내기)을 대신 하고, 나는 "각각으로 뭘 할지"만 콜백에 적는다.

### 3-3. 스토어의 4칸 (그리고 파생값은 저장 안 함)

스토어 객체 안은 딱 네 종류다.

```ts
create<CartStore>()(persist((set, get) => ({
  items: [],                              // 🟢 데이터 원본 (값)
  isOpen: false,                          // 🟢 UI 원본 (값)
  addItem: (item) => set(...),            // 🔴 바꾸기 (set 사용)
  totalKrw: () => get().items.reduce(...) // 🔵 계산 (get 사용)
})))
```

- **값(🟢)** 에는 "기억해야 하는 원본"만 넣는다.
- **파생값(합계·개수)은 저장하지 않는다.** `items`만 있으면 언제든 계산된다.
  따로 저장하면 *"물건 뺐는데 합계 안 바뀌는"* 버그가 난다. (원본은 한 곳 = single source of truth)
- 함수는 **set(바꾸기)** / **get(읽기)** 로 갈린다.

## 4. 딱 하나 이상한 문법: `create()()`

```ts
export const useCartStore = create<CartStore>()(persist(...))
//                                          └┘  └────────┘
//                                        1차 호출  2차 호출
```

괄호가 왜 두 쌍? → **TypeScript 때문에 호출을 둘로 쪼갠 것**이다.

- `create<CartStore>()` — 타입만 확정하고 **새 함수를 리턴** (1차)
- `(persist(...))` — 그 함수를 실행해서 **스토어 완성** (2차)

TS가 "타입 하나는 내가 적고 하나는 추론"을 못 해서 이렇게 나눴다.
타입을 안 붙이면 `create(...)` 한 번으로 끝난다. **이유만 알고 넘어가면 되는 지점.**

## 5. 왜 Context 말고 Zustand?

이유는 두 가지다.

**① 선택 구독(셀렉터)이 된다 — 제일 큰 차이**

Context는 value 객체를 통째로 내려줘서, 하나만 써도 **아무거나 바뀌면 전부 리렌더**된다.

```ts
// Context — user만 써도 cart·theme 바뀌면 같이 리렌더 X
const { user, cart, theme } = useContext(AppContext)

// Zustand — 셀렉터로 조각만 구독, user 안 바뀌면 리렌더 X 
const user = useStore((s) => s.user)
```

**② Provider로 안 감싸도 된다**

Zustand 스토어는 파일(모듈)에 그냥 살아 있어서, `<Provider>`로 트리를 감싸지 않고 **어디서든** 쓴다.

## 느낀 점 
- 경계 감각이 곧 성능이다. 이 기능이 서버(React Query)에 살아야 하는지 클라이언트(Zustand)에 살아야 하는지 정하는 게 서비스 속도와 직결된다는 웅장한 경험 👉🏻👈🏻
- 도구가 문법을 대신해주진 않는다. Zustand가 아무리 편해도, 결국 인자·콜백 같은 기본기를 알아야 '왜 되는지'가 보인다.
- Zustand도 React Query도 결국 같은 패턴. 매개변수로 데이터를 받고, 실행 시점에 그 데이터를 넘긴다. 이 한 패턴만 잡으면 라이브러리가 바뀌어도 읽힌다.
- ⭐️ 깊이 파되, 흐름을 놓치지 말 것 ⭐️ 개념 하나를 오래 붙잡기보다, 데이터가 흐르는 선을 따라가며 그 위에서 깊이 들어가는 게 훨씬 효율적이다.
- 다 파는 게 아니라, 깊이 드릴링할 곳을 고르는 것. 알 때까지 깊이 파는 내 성향은 무기지만, 효율을 함께 재는 융통성이 있어야 그 무기가 산다.
