토스 테크 블로그에 TOI라는 사내 어드민 플랫폼 글이 올라왔다. 자연어로 화면을 요청하면 AI가 React 코드를 만들어주고, 그게 실제 어드민 화면이 된다는 내용이었다. 개념 자체는 이미 여러 곳에서 비슷한 이야기가 나오고 있었는데, 이 글이 달랐던 건 "AI가 코드를 만든 뒤 실제로 돌아가게 만들기까지 어떤 문제가 있었고 어떻게 결정했는지"를 구체적으로 적어둔 부분이었다.

특히 브라우저 안에서 코드를 빌드한다는 대목이 흥미로웠다. 서버 없이 클라이언트에서 TypeScript/JSX를 직접 변환해서 실행한다는 게 어떤 의미인지 조금 더 들여다봤다.

## 1️⃣ TOI가 하려던 것

기존에는 사내 어드민 화면을 만들 때마다 개발, 보안, 배포를 반복해야 했다고 한다. TOI는 이걸 플랫폼으로 묶어서, API를 등록하고 자연어로 요청하면 AI가 React 코드를 만들어주는 방식으로 바꿨다. 사내 공개 이후 6개월 만에 프로젝트 439개와 하위 페이지 2,418개가 만들어졌다는 걸 보면 실제로 쓰이고 있는 것 같다.

핵심 과제는 AI가 만든 코드를 어떻게 실시간으로 화면에 보여주냐는 거였다. 처음에는 Sandpack이라는 외부 툴을 도입했는데 초기 로딩에 47초가 걸렸다고 한다. 결국 직접 만들기로 했고, esbuild-wasm 기반의 브라우저 내 빌드 시스템을 구축했다. TypeScript/JSX를 서버가 아닌 브라우저에서 직접 변환하는 방식이다. 가상 파일 시스템도 4개 레이어로 구성했는데, AI 생성 코드, 사용자 수정 코드, 공통 파일 등을 분리해서 관리하는 구조로 이해했다.

패키지 관리도 고민이 컸던 것 같다. 프로젝트마다 쓰는 패키지 조합이 다르니까 매번 설치하면 느리고, 그렇다고 전부 묶으면 너무 크다. 해결책은 패키지 조합을 해시로 식별해서 S3에 미리 올려두고, Import map으로 런타임에 연결하는 방식이었다. HMR(Hot Module Replacement) 대신 문서 전체를 교체하는 렌더링 방식도 선택했는데, 상태 관리 복잡도를 낮추고 실패한 빌드는 아예 화면에 반영하지 않게 되어 있었다. 결과적으로 로딩이 1.3초로 줄었다.

## 2️⃣ 내가 든 생각

디자이너 입장에서 가장 인상적이었던 건 기술 선택보다 문제 정의 방식이었다. "AI가 코드를 만들어준다"가 아니라 "AI가 만든 코드를 신뢰 가능한 제품 환경에서 실행하게 하려면 뭐가 필요한가"가 실제 풀어야 할 문제였다는 점. 그 과정에서 빌드 시스템, 패키지 관리, 렌더링 방식이 전부 다시 설계돼야 했다.

👉🏻 AI가 결과물을 만들어준다고 해서 그 결과물이 돌아갈 환경이 자동으로 따라오지는 않는다는 게 이 글을 읽고 든 인상이었다.

> 💡 **여기서 드는 질문?**
> AI 생성 코드가 실행되는 환경을 설계하는 일이 점점 중요해진다면, 그게 결국 프로덕트 엔지니어링의 다음 층이 아닐까?

렌더링 방식에서 HMR 대신 전체 교체를 선택한 대목도 기억에 남았다. 더 정교한 방식 대신 단순한 방식을 택한 이유가 명확했는데, 이런 트레이드오프를 글로 남겨두는 게 공부 측면에서는 오히려 더 유용한 것 같았다.

## ⭐️ 마지막으로, 이 글을 정리하면서

정리해보니 이 글의 핵심은 AI 코드 생성 기술 자체보다, 그 결과물을 제품으로 만들기까지의 결정들 쪽이었다. "AI가 다 해준다"와 "AI 결과물이 실제로 제품이 된다" 사이에는 빌드, 패키지, 렌더링 같은 구체적인 문제들이 줄지어 있었다. 그 간격이 생각보다 컸다는 게 지금 남은 인상이다.
