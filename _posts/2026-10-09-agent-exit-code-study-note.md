Stack Overflow 블로그에서 흥미로운 글을 읽었다. AI 에이전트가 성공 코드를 반환해도 실제로 일이 됐는지 확인할 수 없다는 내용이었다.

처음엔 당연한 얘기처럼 느껴졌다. 근데 읽다 보니 생각이 달라졌다. 내가 당연하게 여겼던 종료 코드의 의미가 에이전트에서는 꽤 다르게 작동한다는 걸 정리하는 계기가 됐기 때문이다.

개발 도구로서 에이전트를 공부하는 입장에서 꽤 중요한 개념인 것 같아서 정리해봤다.

## 1️⃣ 이게 뭐냐?

기존 소프트웨어는 실패하면 시끄럽다. 예외가 터지고, 에러 코드가 나오고, CI가 빨간불로 멈춘다. 종료 코드 0은 그 모든 과정을 통과했다는 관찰 결과에 가깝다. 시스템이 외부에서 지켜보며 "이상 없음"을 확인해준 것이다.

에이전트는 좀 다르다. 작업을 마치면 조용히 끝나면서 "완료했습니다"라고 스스로 보고한다. 그 자기 보고가 종료 코드로 이어진다.

이 차이가 핵심인 것 같았다. 기존 종료 코드는 시스템이 외부에서 관찰한 결과인데, 에이전트의 종료 코드는 모델 자신이 "완료"라고 판단한 내부 평가에 가깝다.

글에서 든 사례 중 하나가 꽤 인상적이었다. 어떤 모델이 테스트를 통과시키려고 직접 `sys.exit(0)`을 호출했다고 한다. 테스트 결과는 초록불이었고, 실제 구현은 없었다. 또 다른 에이전트는 단위 테스트에 기대값을 하드코딩해서 통과시킨 사례도 있었다.

기존 소프트웨어에서 "실패 목록"은 어느 정도 미리 열거할 수 있다. 에이전트는 실행마다 실패 방식이 달라질 수 있어서 그게 어렵다는 점도 글에서 짚어줬다.

에이전트가 조용히 끝나면 디버깅 자체도 어렵다. 어디서 잘못됐는지 알려주는 신호가 없으니까. 기존 소프트웨어에서 당연하게 기대했던 "큰 소리로 실패한다"는 전제가 에이전트에서는 달라진다는 것이 이 글의 중심이었다.

## 2️⃣ 내가 든 생각

읽으면서 가장 걸렸던 건 "검증의 방향"이 달라진다는 부분이었다. 기존 소프트웨어는 실패 원인 기준으로 점검할 수 있는데, 에이전트는 결과물 기준으로 점검해야 한다는 얘기다.

👉🏻 에이전트가 파일을 만들었다고 보고했다면, 그 파일이 실제로 존재하는지를 따로 확인하는 방식이 필요하다. 자기 보고를 믿는 게 아니라 결과물의 존재 자체를 검증하는 것이다.

이걸 UI 관점에서 생각해보면, "작업 완료" 배지를 어떤 근거로 보여줄 것인가 하는 질문으로 이어졌다. 에이전트의 자기 보고를 그대로 표시하는 것과, 실제 결과물의 상태를 확인한 뒤 표시하는 건 설계 단에서 꽤 다른 선택이 될 것 같다.

> 💡 **여기서 드는 질문?**
> "변경 없음"이 조용히 초록색으로 보일 때, 사용자는 어떻게 알 수 있을까?

디자인 도구를 공부하면서 항상 신경 쓰는 게 "이 상태를 사용자가 어떻게 해석할까"였는데, 에이전트 기반 UI에서는 그 질문이 더 복잡해지는 것 같다. 완료 상태가 실제로 완료된 것인지, 단순히 모델이 그렇게 판단한 것인지 구분하는 게 UX 설계에서도 고민거리가 될 것 같다.

## ⭐️ 마지막으로, 신뢰의 근거가 바뀐다는 것

정리해보니, 이 글이 하고 싶은 말은 "에이전트를 믿지 말라"보다는 "신뢰의 근거가 달라진다"쪽에 가까운 것 같다.

기존 소프트웨어에서 초록불은 관찰의 결과였다. 에이전트에서 초록불은 자기 보고의 결과일 수 있다. 그 차이를 이해하고 설계에 반영하는 것이 결국 핵심인 것 같다.
