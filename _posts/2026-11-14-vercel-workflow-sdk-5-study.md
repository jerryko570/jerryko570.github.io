Vercel 블로그에서 Workflow SDK 5 공개 글을 읽었다. 처음엔 그냥 버전 업데이트겠거니 했는데, 읽다 보니 "실행 중인 코드가 도중에 멈추면 어떻게 될까"라는 질문에서 시작된 도구라는 게 흥미로웠다.

async/await는 많이 봤는데, 그 코드가 서버 배포 중간에 중단되거나 크래시가 나면 어떻게 되는지는 생각해본 적이 없었다. Workflow SDK는 바로 그 상황을 다루려고 만들어진 도구인 것 같다.

## 1️⃣ 이게 뭐냐?

Workflow SDK의 기본 아이디어는 평범한 async JavaScript 코드를 쓰되, 그 코드가 중간에 멈추고 다시 시작할 수 있도록 각 단계의 입출력을 저장해 두는 것이다. 그걸 "step"이라고 부른다.

예를 들어 주문 처리 로직이 step 10번 중 7번까지 실행됐는데 배포가 되면, 다음 실행 때 7번부터 이어 간다. "이벤트 로그를 저장해뒀다가 replay한다"는 개념인데, 공부하면서 이게 꽤 근본적인 접근이라고 느꼈다.

v5에서 여러 가지가 바뀌었는데, 그중 두 가지가 특히 눈에 들어왔다.

첫 번째는 암호화다. step의 입출력이 이벤트 로그로 저장되는 구조인 만큼, 거기에 민감한 데이터가 들어있을 수 있다. 이제는 그 데이터를 코드 밖으로 나가기 전에 AES-256-GCM으로 암호화한다고 한다. Vercel 측에서도 평문을 볼 수 없고, 복호화는 로컬에서 직접 해야 한다.

두 번째는 리전 배치다. 이전까지는 모든 run 데이터가 하나의 고정된 리전에 저장됐는데, v5부터는 run을 시작할 때 `region` 옵션으로 데이터가 저장될 위치를 직접 지정할 수 있다. 한국이나 유럽 쪽에서 실행되는 워크플로우라면 의미 있는 변화인 것 같다.

## 2️⃣ 내가 든 생각

Workflow SDK를 처음 접했을 때 "이건 그냥 Queue 같은 건가?" 싶었는데, 이벤트 로그 replay 개념을 보고 나서 좀 다르게 느껴졌다. Queue는 메시지를 전달하는 구조고, Workflow SDK는 코드 실행 흐름 자체를 저장하는 쪽에 가까운 것 같다.

암호화 얘기가 흥미로웠던 건, 평소에 async 코드를 쓸 때 "도중에 무슨 일이 생기면?"을 별로 안 생각했기 때문이다. await 사이에 데이터가 중간 어딘가에 저장될 수 있다는 걸 이번에 처음 의식하게 됐다. Workflow SDK 같은 durable 실행 도구는 그 "사이"를 명시적으로 다루는 도구라는 인상을 받았다.

👉🏻 디자이너 관점에서 보면, "실행 중간에 상태를 어떻게 처리하느냐"는 결국 사용자한테도 영향을 미치는 문제다. 주문이 처리되다 중단됐을 때 사용자에게 뭐가 보이느냐, 같은 질문이 연결된다.

> 💡 **여기서 든 질문:** 개발자가 step 로그에 의도치 않게 민감한 데이터를 넣는 경우는? 암호화가 된다고 해도, 어떤 데이터를 로그에 담느냐는 여전히 개발자 책임인 것 같다.

성능도 꽤 달라진 것 같다. 증분 replay 방식으로 바꿨다는 구조적인 변화는 이해가 됐다. 이벤트 로그 전체를 매번 다시 재생하면 로그가 길어질수록 오버헤드가 커지는 게 당연하니까. 발표 글에서 대규모 step 처리 완료 시간이 크게 줄었다고 했는데, 내부 측정치라 얼마나 보편적으로 적용될지는 모르겠다.

## ⭐️ 마지막으로, 프론트엔드 공부하면서 느낀 것

이번에 Workflow SDK를 공부하면서, 비동기 코드가 "언제 실패할 수 있는지"를 별로 생각 안 했다는 걸 알게 됐다. async/await가 단순해 보이지만, 그게 실제 서버에서 돌아갈 때는 배포, 크래시, 타임아웃 같은 변수가 많다.

정리해보니 중요한 건 더 빠른 실행이라기보다, 실패를 전제로 했을 때 코드가 어떻게 동작하느냐 쪽이었다.
