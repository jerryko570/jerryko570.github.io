GitHub Blog에서 GitHub Copilot 앱의 초심자 가이드를 읽었다. AI가 만든 코드를 확인하려면 에디터, 터미널, 브라우저 사이를 왔다 갔다 하는 게 기본 흐름인 줄 알았는데, Copilot 앱이 그 과정을 패널로 묶어서 한 화면에 배치했다는 점이 궁금해졌다. 직접 쓴 건 아니고 문서를 읽으면서 정리해봤다.

처음엔 '탭 전환이 그렇게 큰 문제인가?' 싶었는데, 읽다 보니 단순히 편의 기능을 추가한 게 아니라 AI 코드를 검증하는 루프 자체를 화면 안에 구성했다는 쪽으로 이해가 기울었다.

## 1️⃣ 이게 뭐냐?

Copilot 앱이 제공하는 건 Diff 패널, Terminal 패널, Browser 패널의 세 가지 조합이다. AI가 제안한 코드를 검토하고, 직접 실행해보고, 화면에서 결과를 확인하는 과정이 탭 전환 없이 한 곳에서 이뤄질 수 있도록 배치했다.

Diff 패널은 코드 변경사항을 녹색(추가)·빨간색(삭제)으로 보여준다. 코드 전체를 처음부터 다시 읽지 않아도 어디가 바뀌었는지 파악하기 수월한 구조인 것 같다. 변경을 수락하거나 거절하고, 특정 줄에 코멘트를 남기는 것도 이 패널 안에서 가능하다.

Terminal 패널은 `npm run dev` 같은 명령어를 앱 안에서 직접 실행한다. Run 버튼으로 스크립트를 미리 설정해두면, 코드 수락 후 서버가 자동으로 올라오는 흐름을 만들 수 있는 것 같다. 여러 터미널 창을 동시에 열어두는 것도 가능하다고 한다.

Browser 패널에는 "Pick & Polish"라는 도구가 포함돼 있다. 화면에서 특정 요소를 선택하면 AI와 함께 조정할 수 있는 방식인데, 단순한 미리보기 탭이 아니라 확인하면서 수정을 요청하는 인터페이스까지 연결돼 있는 것 같다. 세 패널의 순서 자체가 코드 검증의 단계를 따르는 구조인 것 같다.

## 2️⃣ 내가 든 생각

Figma에서 레이어를 선택하고 우측 패널에서 속성을 바꾸는 흐름이랑, Browser 패널에서 요소를 클릭하고 수정을 요청하는 흐름이 비슷한 모양새인 것 같다는 생각이 들었다. 처리 방식 자체는 다르겠지만, "보면서 바꾸는" 패턴이라는 점에서 디자이너 입장에서 낯설지 않게 느껴졌다.

👉🏻 탭 전환을 없애는 게 편의 기능처럼 보이지만, 코드 검토 과정에서 맥락이 끊기지 않는다는 게 실제로는 꽤 중요한 부분인 것 같다. 에디터에서 터미널로, 터미널에서 브라우저로 이동할 때마다 "내가 뭘 확인하려고 했더라"를 다시 떠올려야 하는 순간이 생기니까.

> 💡 **여기서 드는 질문?** Pick & Polish가 어느 범위까지 수정을 지원하는 건지가 궁금해졌다. 스타일 조정 정도인지, 컴포넌트 구조를 건드리는 요청도 가능한 건지.

AI 코드를 어떻게 검증하느냐는 요즘 자꾸 나오는 주제인 것 같은데, Copilot 앱의 방향은 그 검증 단계를 흐름 안에 묶어버리는 방식인 것 같다. Diff 확인 → 실행 → 화면 확인을 하나의 루프로 이어두면 중간에 맥락을 잃을 가능성이 줄어드는 거니까. 초심자 가이드라는 타이틀이 붙어있지만, 이 루프를 어떻게 구성하느냐는 익숙한 개발자에게도 의미 있는 질문인 것 같다.

## ⭐️ 마지막으로, 도구 설계를 공부하면서 느낀 점

공부 끝에 남은 건 패널 세 개라기보다 코드 검증 루프 하나라는 인상이다. 탭이 사라진 게 아니라 Diff → 실행 → 확인이라는 단계가 하나의 화면 안에 닫혀 있다는 게 이 도구의 핵심인 것 같았다. 그 루프가 잘 닫혀 있을수록, 검토가 덜 번거롭게 느껴질 거라는 생각이 남았다.
