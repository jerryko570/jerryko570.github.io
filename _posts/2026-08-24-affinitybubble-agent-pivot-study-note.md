PXD Story에서 어피니티버블 관련 글을 읽었다. 정성 데이터 분석 도구인데, 이번에 방향을 꽤 크게 틀었다는 내용이었다.

원래는 인터뷰나 앱 리뷰 같은 텍스트 데이터를 비슷한 것끼리 묶어 시각화해주는 도구였는데, 이번에 API + 에이전트 중심으로 피봇했다고 한다. 새 기능이 추가됐다는 것보다 방향을 바꾼 이유가 더 흥미로워서, 공부하면서 정리해봤다.

## 1️⃣ 이게 뭐냐?

어피니티버블은 UXR에서 자주 하는 어피니티 다이어그램 작업을 자동화해주는 도구다. 포스트잇에 인터뷰 내용 옮겨 적고 비슷한 것끼리 묶는 작업을, 텍스트 데이터 기반으로 자동 세그먼트화해서 버블 차트로 보여준다.

서비스를 운영하면서 나온 공통된 피드백이 있었다고 한다. "데이터 오버뷰 파악에는 유용한데, 실제 업무에서 필요한 깊은 분석은 부족하다"는 것. 팀마다 원하는 분석 방식이 다 달랐고, 그걸 모두 UI로 만들기엔 기획 비용이 너무 컸다.

동시에 많은 사용자들이 이미 AI 에이전트를 업무에 쓰고 있었다는 맥락도 있었다. 그래서 나온 결론이 "새 UI를 발명하지 말고, 에이전트가 이미 쓰고 있는 도구를 잘 만들어 건네주자"였다.

논리는 이렇다. GUI는 사람의 인지 부담을 줄여주기 위한 거고, 에이전트한테는 오히려 처리 비용이 된다. 텍스트와 API가 에이전트한테는 훨씬 빠르고 저렴하다. 그래서 API와 시각화 라이브러리를 에이전트가 스킬처럼 가져다 쓸 수 있는 형태로 제공하는 방향으로 피봇했다.

## 2️⃣ 내가 든 생각

"GUI가 에이전트한테 비용"이라는 표현이 꽤 낯설게 느껴졌다. UI가 더 쓰기 쉬운 거라고 당연하게 생각해왔는데, 그건 사람 기준 얘기고, 에이전트한테는 텍스트와 API가 오히려 더 자연스러운 인터페이스라는 얘기다.

글에서 CLI → GUI → Agent UI라는 흐름을 짧게 짚고 넘어갔는데, 그 한 줄이 좀 오래 남았다. 사람을 위한 인터페이스를 잘 만드는 게 당연히 중요한 일이라고 생각해왔는데, 도구의 주 사용자가 에이전트라면 API 설계와 문서 작성이 UI 설계만큼 중요한 설계 작업이 되는 거다.

👉🏻 "누구를 위한 인터페이스인가"라는 질문이, 에이전트가 등장하면서 다시 열린 것 같다는 인상이었다.

> 💡 **그러면 에이전트를 주 사용자로 두는 도구는 어떻게 설계되어야 할까?** 사람 대상의 UX 원칙이 그대로 통할지, 아니면 다른 기준이 필요한 건지.

이번에 추가된 ABSA(속성기반감성분석) 기능도 눈에 들어왔다. "배송은 좋은데 포장은 별로다" 같은 문장을 속성 단위로 쪼개서 분석하는 방식인데, 리뷰 데이터에서 "전체 평점은 높은데 특정 부분 불만이 많다"는 상황을 많이 봐온 터라, 어떤 필요에서 나온 기능인지 자연스럽게 와닿았다. 제품을 설계하는 입장에서 보면 전체 만족도보다 속성별 온도 차이가 더 유용한 정보인 경우가 많다.

## ⭐️ 마지막으로, 도구 설계 관점에서 공부하며 느낀 점

정리해보니 이 글에서 흥미로웠던 건 새 기능 자체보다, "어떤 사용자를 위한 도구인가"를 다시 정의한 과정이었다. 사람을 위한 GUI에서, 에이전트가 스킬로 가져다 쓸 수 있는 API로.

이런 방향 전환 이야기를 보면 늘 같은 질문이 생기는 것 같다 — 사용자가 바뀌면, 좋은 도구의 기준도 처음부터 다시 써야 하는 건지.
