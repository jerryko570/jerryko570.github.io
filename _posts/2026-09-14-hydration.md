## 이 글의 목표

지난번 Zustand `persist`로 장바구니를 `localStorage`에 붙여놨는데, 새로고침할 때마다 콘솔에 **hydration 경고**가 떴다.
"저장은 잘 되는데 왜 경고가 나지?" 싶어서 넘기려다, 이 경고가 결국 **SSR·CSR·Hydration을 안 보고 있어서** 나는 거라 파보기로 했다.

React를 이제 막 시작한 사람도 읽을 수 있게, 용어부터 하나씩 깔고 간다.
목표는 **"화면 하나가 서버에서 브라우저까지 오는 길"** 을 끝까지 따라가 보는 것.

### 세 줄 요약

1. 화면은 **서버에서 한 번, 브라우저에서 한 번, 총 두 번** 그려진다.
2. 그 **두 결과가 다르면** React가 경고를 띄운다. 이게 hydration 경고.
3. `localStorage`처럼 **브라우저에만 있는 값**은 첫 렌더가 아니라 `useEffect`에서 써야 한다.

---

## 0. 용어부터 한 줄씩

파기 전에 단어 뜻만 잡고 가자. 이 네 개면 이 글은 다 읽힌다.

| 용어 | 한 줄 정의 |
| --- | --- |
| **CSR** (Client Side Rendering) | 화면을 **브라우저가** JS로 그리는 방식 |
| **SSR** (Server Side Rendering) | 화면을 **서버가** 미리 HTML로 그려서 보내는 방식 |
| **Hydration** | 서버가 보낸 HTML 위에 React가 **이벤트·상태를 붙이는** 단계 |
| **클라이언트 컴포넌트** | `useState`, `useEffect` 같은 걸 쓰는 컴포넌트 (브라우저에서도 동작해야 하는 쪽) |

`hydrate`는 원래 "수분을 채우다"라는 뜻이다. 이 비유가 생각보다 정확했다.
서버가 보내주는 건 **마른 껍데기(HTML)**, 브라우저가 그 위에 **상태와 이벤트를 부어서** 살려낸다.

---

## 1. 왜 이런 구조가 생겼을까

세 개를 따로따로 외우니까 안 붙었다. **하나의 흐름**으로 이으니까 한 번에 읽혔다.
시작은 옛날 방식의 불편함이었다.

```
① 옛날 순수 CSR (예전 CRA 방식)
      브라우저가 화면을 그림 → JS 도착 전까지 흰 화면 😵
      <div id="root"></div>   👈🏻 진짜 빈 껍데기, JS 와야 채워짐
      │
      │  "첫 화면이 너무 느리다" → 이 문제를 없애려고
      ▼
② SSR 등장
      그리는 일을 '서버로' 넘김 → 내용 채운 HTML을 미리 보냄
      <span>3개</span>         👈🏻 내용은 꽉 참. 근데 아직 안 움직임
      │
      │  서버가 그렸을 뿐 JS는 아직 안 붙음 → 그래서
      ▼
③ Hydration
      브라우저가 그 HTML 위에 JS를 부어서 → 이제 클릭·상태변경 됨 ✅
      │
      │  근데 서버엔 브라우저가 없어서(= localStorage 못 봄)
      ▼
④ (어긋나면) 경고 ⚠️
      서버 0개 vs 브라우저 3개 → React가 "화면이 다른데?" → hydration 경고
```

한 줄로 이으면 이렇게 된다.

> **CSR의 흰 화면** → 그걸 없애려고 **SSR**(그리기를 서버로) → 서버가 그린 위에 JS를 붙이는 **Hydration** → 근데 서버·브라우저 값이 **어긋나서 경고**.

포인트는 ②의 "서버로 넘김"이 공짜가 아니라는 거다.
**빠른 첫 화면을 얻은 대가로 hydration이라는 숙제가 생긴 것.** 내가 만난 경고가 바로 그 숙제였다.

### CSR과 SSR, 사용자 입장에서 뭐가 다른가

```
CSR:  HTML 받기(빈 껍데기) → JS 다운로드 → JS 실행 → 그제서야 화면 표시
SSR:  완성된 HTML 받기 → 바로 화면 표시(아직 안 눌림) → JS 다운로드 → hydration → 이제 눌림
```

SSR은 **"보이는 시점"이 앞당겨진 것**이지, "동작하는 시점"이 앞당겨진 게 아니다.
이 둘을 구분하고 나서야 hydration이 왜 필요한지가 이해됐다.

## 2. 전체 흐름 한 장으로

내가 제일 오래 붙잡고 있던 게 **"누가 먼저 실행되는가"** 였다. 순서를 끝까지 적어보니 정리됐다.

```
1. 브라우저 요청                        ← 시작은 브라우저 (주소 입력)
2. 서버에서 렌더링 → HTML 생성          ← 컴포넌트 1차 실행 (서버)
3. 브라우저가 HTML 표시                 ← 보이지만 아직 안 눌림
4. JS 번들 다운로드
5. Hydration                            ← 컴포넌트 2차 실행 (브라우저)
     - 결과 계산
     - 서버가 보낸 HTML과 비교
     - 기존 DOM에 이벤트·상태 연결
6. useEffect 실행                       ← 이제 완전히 동작
```

여기서 헷갈리기 쉬운 세 가지를 따로 떼어 두면 이렇다.

- **요청 순서**는 브라우저가 먼저다. (사용자가 주소를 쳐야 시작하니까)
- **코드 실행 순서**는 서버가 먼저다. 브라우저는 서버 결과를 **이어받아 검증하고 연결**한다.
- **화면에 보이는 순서**는 HTML이 먼저다. 사용자는 hydration 전에 이미 내용을 볼 수 있고, 그 시점엔 버튼을 눌러도 반응이 없다.

3번과 5번 사이의 저 틈. 여기가 SSR의 이득이자, 모든 hydration 문제의 출발점이다.

---

## 3. Hydration의 유일한 규칙

처음엔 "그냥 JS 붙는 거 아냐?" 했는데, 조건이 하나 붙어 있었다.

> **컴포넌트는 서버에서 1번, 브라우저에서 1번, 총 두 번 실행되고 — 두 결과가 같아야 한다.**

React는 hydration 할 때 **서버가 그린 HTML과 자기가 첫 렌더로 만든 결과가 똑같다고 믿고** 이벤트만 얹는다.
처음부터 다시 그리는 게 아니라 **이미 있는 DOM을 재활용**하는 거다. 그래야 빠르니까.

```
서버 HTML:    <p>0개</p>     ← 서버가 그려서 보낸 것
클라 첫 렌더:  <p>0개</p>     ← React가 브라우저에서 처음 계산한 것
                             둘이 같음 → 조용히 연결 ✅
```

즉 hydration은 **DOM을 새로 만드는 게 아니라 "계산 + 비교 + 연결"** 이다.
그래서 이 둘이 다르면 React가 당황한다. "내가 붙일 자리랑 화면이 다른데?"

### 두 결과를 다르게 만드는 대표 범인들

렌더링 중에 이런 걸 쓰면 서버와 브라우저의 결과가 달라진다.

- `localStorage`, `sessionStorage` — 서버에는 아예 없음
- `window`, `document` — 서버에는 없음
- `Date.now()`, `new Date()` — 서버에서 그린 시각 ≠ 브라우저가 그리는 시각
- `Math.random()` — 매번 다름

> 정리하면: **이런 값들은 렌더링 중이 아니라 `useEffect` 안에서 써야 한다.**
> `useEffect`는 브라우저에서만, 그것도 hydration이 끝난 뒤에 돌기 때문이다.

## 4. 그래서 내 경고는 왜 떴나

내 케이스로 돌아와서. 장바구니 개수를 화면에 이렇게 띄우고 있었다.

```tsx
const count = useCartStore((s) => s.items.length)
return <span>{count}개</span>
```

문제는 **서버와 브라우저가 서로 다른 값**을 봤다는 거다.

```
서버(SSR):  localStorage 없음 → items = []      → <span>0개</span>
브라우저:   localStorage에서 3개 복원됨 → items 3 → <span>3개</span>
                                    ┗━ 서버 0 ≠ 클라 3 → hydration 경고 ⚠️
```

`localStorage`는 **브라우저에만 있는 창고**다. 서버에는 없다.
그러니 서버는 무조건 "빈 장바구니(0개)"로 HTML을 그려서 보낸다.
근데 Zustand `persist`는 **스토어가 만들어지는 시점에 거의 바로** 복원을 해버린다. 브라우저는 그 복원된 "3개"로 첫 렌더를 하니까, **첫 순간 두 값이 어긋난다.**

경고 자체가 곧 버그는 아니다. 다만 React가 "그럼 내가 다시 그릴게" 하고 그 부분을 버리기 때문에 **깜빡임**이 생기거나, 애써 얻은 서버 렌더의 이점이 사라진다. 그게 찜찜했던 거다.

---

## 5. 어떻게 풀었나

해법은 결국 한 문장으로 모인다. **"서버와 클라이언트의 첫 렌더를 억지로 맞춰준다."**
맞춘 다음에, 진짜 값은 그 뒤에 넣는다.

### 5-1. `skipHydration` + 직접 `rehydrate` (내가 쓴 방법)

persist에는 이걸 위한 스위치가 있었다.

```ts
persist(
  (set, get) => ({ /* ... */ }),
  {
    name: 'cart-storage',
    skipHydration: true,   // 👈🏻 자동 복원을 잠깐 미룸
  }
)
```

`skipHydration: true`를 켜면 persist가 **첫 렌더 때는 복원을 안 한다.**
그래서 서버도 0개, 클라 첫 렌더도 0개 → **둘이 같아져서 경고가 사라진다.**

그다음, **브라우저에 완전히 올라온 뒤에** 직접 복원을 불러준다.

```tsx
useEffect(() => {
  useCartStore.persist.rehydrate()   // 이제 안전하게 localStorage 값 복원
}, [])
```

순서로 보면 이렇게 된다.

```
서버: 0개 그림  →  클라 첫 렌더: 0개 (같음, 연결 성공)  →  useEffect: 3개로 복원
                          ┗━ 경고 없음 ✅                  ┗━ 화면 자연스럽게 갱신
```

### 5-2. `mounted` 플래그 (더 일반적인 패턴)

persist가 아니어도 쓸 수 있는, 같은 원리의 방법. 다른 라이브러리나 직접 만든 상태에도 그대로 쓰인다.

```tsx
const [mounted, setMounted] = useState(false)
useEffect(() => setMounted(true), [])

const count = useCartStore((s) => s.items.length)
return <span>{mounted ? count : 0}개</span>
//              ┗━ 첫 렌더는 무조건 0 → 서버와 동일 → 이후 진짜 값으로 갱신
```

원리는 똑같다. **첫 렌더는 서버와 같은 값으로 맞추고, 그 뒤에 진짜 값으로 바꾼다.**

### 5-3. 이건 근본 해결이 아니었다

검색하면 자주 나오는 게 이거다.

```ts
const items = typeof window !== 'undefined' ? restore() : []
```

"서버면 빈 값, 브라우저면 복원값" — 되는 것 같지만 아니다.
브라우저의 **첫 렌더에서 바로 복원값을 써버리니까 또 어긋난다.**
`window` 체크는 "여기가 브라우저냐"만 알려줄 뿐, **"hydration이 끝났냐"는 알려주지 않는다.**
순서(첫 렌더는 맞추고, 그 이후에 갱신)를 안 지키면 소용없었다.

`suppressHydrationWarning`도 마찬가지다. 경고만 가릴 뿐 어긋남 자체는 그대로다. 시각처럼 정말 어쩔 수 없는 곳에만 쓰는 게 맞다.

## 6. 헷갈렸던 지점

### 6-1. "서버 컴포넌트"와 "SSR"은 다른 말

처음엔 같은 건 줄 알았는데 아니었다.

- **SSR** = 화면을 *언제 어디서 그리냐*의 문제 (서버에서 HTML을 미리 그림)
- **Server Components** = 컴포넌트가 *어느 쪽 소속이냐*의 문제 (JS를 클라이언트로 안 보냄)

내 장바구니처럼 `useState`·`useStore`를 쓰는 건 전부 **클라이언트 컴포넌트**다.
그런데 클라이언트 컴포넌트도 **첫 HTML은 서버가 그린다.**
"클라이언트 컴포넌트니까 서버랑 상관없겠지"가 착각이었고, hydration 경고가 바로 여기서 났던 거였다.

### 6-2. 경고는 버그가 아니라 신호였다

경고 문구를 "없애야 할 것"으로만 보면 `suppressHydrationWarning`으로 덮게 된다.
근데 이 경고는 **"서버와 브라우저가 지금 다른 걸 보고 있다"** 는 신호였다. 덮으면 신호만 사라진다.

## 7. 마지막 체크리스트

새 컴포넌트를 만들 때 이것만 훑으면 된다.

- [ ] 렌더링 중에 `window` / `localStorage`를 읽고 있진 않은가?
- [ ] 렌더링 중에 `Date.now()` / `Math.random()`을 쓰고 있진 않은가?
- [ ] 브라우저에만 있는 값이라면 → `useEffect` 안으로 옮겼는가?
- [ ] **첫 렌더**는 서버와 같은 값으로 맞췄는가? (`mounted`, `skipHydration`)

## 느낀 점

- 경고 하나가 사실은 구조를 안 보고 있다는 신호였다. "저장 잘 되는데 왜?"에서 멈췄으면 SSR·CSR을 깊이 알지 못했을 듯.
- hydration은 결국 **"서버가 그린 그림과 브라우저의 첫 렌더를 같게 맞추는 일"** 에 가깝다. 해결책이 다 이 한 문장으로 설명된다.
- 전직 디자이너 눈으로 보면, 깜빡임 같은 사소한 UX 버그 뒤에 이런 렌더링 순서가 숨어 있는 게 흥미로웠다. 화면이 두 번 그려진다는 걸 알고 나니 로딩 깜빡임이 다르게 보인다.
- ⭐️ 정리해보니 hydration은 새로운 개념이라기보다, **"화면이 두 번 그려진다"는 사실 하나를 받아들이는 일**에 가까웠다. 그 사실만 잡으니 경고 메시지가 다 읽혔다.
