## 이 글의 목표

지난번 Zustand `persist`로 장바구니를 `localStorage`에 붙여놨는데, 새로고침할 때마다 콘솔에 **hydration 경고**가 떴다.
"저장은 잘 되는데 왜 경고가 나지?" 싶어서 넘기려다, 이 경고가 결국 **SSR·CSR·Hydration**을 안 보고 있어서 나는 거라 파보기로 했다.

그래서 이번엔 화면 하나를 골라 **서버가 그린 HTML → 브라우저가 이어받는 순간**까지 따라가 봤다.

---

## 0. 큰 그림: 화면은 두 번 그려진다

먼저 큰 그림 한 장. 핵심은 **화면이 한 번에 안 뜨고, 두 단계로 만들어진다**는 거다.

```
━━━ 서버에서 (SSR) ━━━
① 서버가 컴포넌트(함수)를 미리 실행
      │  → 완성된 HTML 문자열을 만듦
      ▼
② 브라우저가 그 HTML을 먼저 화면에 그림   👈🏻 아직 '그림'일 뿐, 버튼 눌러도 반응 X

━━━ 브라우저에서 (CSR / Hydration) ━━━
      │  JS 번들 도착 → React가 다시 실행
      ▼
③ 서버가 준 HTML 위에 React가 이벤트·상태를 '연결'   👈🏻 이게 Hydration
      │
      ▼
④ 이제부터 클릭·상태변경 다 됨 (완전히 살아있는 화면)
```

- **SSR** = 서버가 HTML을 미리 그려서 보냄 → 첫 화면이 빨리 뜬다
- **CSR** = 브라우저가 JS로 화면을 그림 → 인터랙션은 여기서
- **Hydration** = 서버가 준 마른 HTML에 React가 **물을 붓는** 단계

`hydrate`가 원래 "수분을 채우다"라는 뜻인데, 이 비유가 생각보다 정확했다.
서버가 준 건 **마른 껍데기(HTML)**, 브라우저가 그 위에 **상태와 이벤트를 부어서** 살려낸다. (맞나?)

---

## 1. Hydration이 뭔데?

처음엔 "그냥 JS 붙는 거 아냐?" 했는데, 조건이 하나 붙어 있었다.

React는 hydration 할 때, **서버가 그린 HTML과 자기가 첫 렌더로 만든 결과가 똑같다고 믿고** 이벤트만 얹는다.
처음부터 다시 그리는 게 아니라, **이미 있는 DOM을 재활용**하는 거다. 그래야 빠르니까.

```
서버 HTML:  <p>0개</p>       ← 서버가 그려서 보낸 것
클라 첫 렌더: <p>0개</p>       ← React가 브라우저에서 처음 계산한 것
                              둘이 같음 → 조용히 연결
```

그래서 **이 둘이 다르면** React가 당황한다. "내가 붙일 자리랑 화면이 다른데?"
그게 바로 그 경고였다.

---

## 2. 왜 경고가 떴나 — 서버는 localStorage를 모른다

내 케이스로 돌아와서. 장바구니 개수를 화면에 이렇게 띄우고 있었다.

```tsx
const count = useCartStore((s) => s.items.length)
return <span>{count}개</span>
```

문제는 **서버와 브라우저가 서로 다른 값**을 봤다는 거다.

```
서버(SSR):  localStorage 없음 → items = []      → <span>0개</span>
브라우저:   localStorage에 3개 복원됨 → items 3  → <span>3개</span>
                                    ┗━ 서버 0 ≠ 클라 3 → hydration 경고 ⚠️
```

`localStorage`는 **브라우저에만 있는 창고**다. 서버에는 없다.
그러니 서버는 무조건 "빈 장바구니(0개)"로 HTML을 그려서 보낸다.
근데 브라우저는 `persist`가 복원한 "3개"로 첫 렌더를 하니까, **첫 순간 두 값이 어긋난다.**

경고 자체가 버그는 아니었다. 근데 React가 "그럼 내가 다시 그릴게" 하고 그 부분을 버리기 때문에, **깜빡임**이 생기거나 서버 렌더의 이점이 사라진다. 그게 찜찜했던 거다.

---

## 3. 그래서 어떻게 풀었나

방법은 결국 하나로 모였다. **"서버랑 클라 첫 렌더를 억지로 맞춰준다."**
persist에는 이걸 위한 스위치가 있었다.

```ts
persist(
  (set, get) => ({ ... }),
  {
    name: 'cart-storage',
    skipHydration: true,   // 👈🏻 자동 복원을 잠깐 미룸
  }
)
```

`skipHydration: true`를 켜면, persist가 **첫 렌더 때는 복원을 안 한다.**
그래서 서버도 0개, 클라 첫 렌더도 0개 → **둘이 같아져서 경고가 사라진다.**

그다음 **브라우저에 완전히 올라온 뒤에** 직접 복원을 불러준다.

```tsx
useEffect(() => {
  useCartStore.persist.rehydrate()   // 이제 안전하게 localStorage 값 복원
}, [])
```

`useEffect`는 **브라우저에서만, 그리고 hydration이 끝난 뒤에** 도니까 여기서 복원하면 어긋날 일이 없다.
순서로 보면 이렇게 된다.

```
서버: 0개 그림  →  클라 첫 렌더: 0개 (같음, 연결 성공)  →  useEffect: 3개로 복원
                                    ┗━ 경고 없음 ✅        ┗━ 화면 자연스럽게 갱신
```

---

## 4. 헷갈렸던 지점 정리

파면서 계속 걸렸던 것 두 개만 남겨둔다.

### 4-1. "서버 컴포넌트"랑 "SSR"은 다른 말

처음엔 같은 건 줄 알았는데 아니었다.

- **SSR** = 화면을 *언제 어디서 그리냐*의 문제 (서버에서 HTML 미리 그림)
- **Server Components** = 컴포넌트가 *어느 쪽 소속이냐*의 문제 (JS를 클라로 안 보냄)

내 장바구니처럼 `useState`·`useStore` 쓰는 건 다 **클라이언트 컴포넌트**다.
근데 클라이언트 컴포넌트도 **SSR로 첫 HTML은 서버가 그린다.** 그래서 hydration 경고가 여기서 난 거였다.

### 4-2. `typeof window` 체크는 근본 해결이 아니었다

검색하면 자주 나오는 게 이거다.

```ts
const items = typeof window !== 'undefined' ? restore() : []
```

"서버면 빈 값, 브라우저면 복원값" — 되긴 되는데, 결국 **첫 렌더는 서버랑 맞춰야** 경고가 안 난다.
`window` 체크로 브라우저에서 바로 복원값을 쓰면 **또 어긋난다.** 순서(첫 렌더는 맞추고, 이후에 갱신)를 안 지키면 소용없었다.

---

## 느낀 점

- 경고 하나가 사실은 구조를 안 보고 있다는 신호였다. "저장 잘 되는데 왜?"에서 멈췄으면 SSR·CSR를 깊이 있게 알지 못했을 듯.
- hydration은 결국 **"서버가 그린 그림과 브라우저 첫 렌더를 같게 맞추는 일"** 에 가깝다. 해결책도 다 이 한 문장으로 설명됨.
- 전직 디자이너 눈으로 보면, 깜빡임 같은 사소한 UX 버그 뒤에 이런 렌더링 순서가 숨어 있는 게 흥미로웠다. 화면이 두 번 그려진다는 걸 알고 나니 로딩 깜빡임이 다르게 보인다.
- ⭐️ 정리해보니 hydration은 새로운 개념이라기보다, **"화면이 두 번 그려진다"는 사실 하나를 받아들이는 일**에 가까웠다. 그 사실만 잡으니 경고 메시지가 다 읽혔다.
