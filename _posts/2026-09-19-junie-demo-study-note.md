JetBrains 블로그에서 Junie `/demo`라는 새 모드 발표가 있었다. 제목만 봤을 때는 단순한 미리보기 기능이겠거니 했는데, 읽어보니 방향이 좀 달랐다.

코드를 다 짜고 테스트가 통과됐을 때, 그다음 단계가 항상 번거롭다. 앱을 직접 켜고, 해당 화면을 찾고, 흐름대로 눌러보는 과정 — 에이전트가 코드는 짜줬는데 그 확인 과정은 여전히 사람이 한다는 게 이 발표의 출발점인 것 같았다.

## 1️⃣ 이게 뭐냐?

Junie `/demo`는 코드 변경사항의 동작을 자동으로 녹화해주는 모드다. 확인하고 싶은 내용을 설명하면 Junie가 앱을 빌드하고 실행한 뒤 UI를 직접 조작하며 영상으로 기록한다.

결과물이 단순한 화면 녹화가 아니라는 점이 흥미로웠다. HTML 리포트 형태로 나오는데, 영상 안에 어떤 동작을 했는지 설명 슬라이드가 포함되고 자동 자막도 붙는다. PR에 올리면 코드 변경 내용과 함께 실제 동작을 같이 보여줄 수 있는 구조다.

원문에 "A diff explains the code change. A demo adds the behavior you can see"라는 표현이 있었다. 기능 설명 문장 중에서 이게 제일 명확하게 다가왔다.

## 2️⃣ 내가 든 생각

디자이너 입장에서 이 흐름이 익숙하게 느껴졌다. 디자인 프로세스에서도 화면을 넘길 때 "이게 어떻게 동작하는지"를 별도로 설명하는 작업이 항상 있었다. Figma 프로토타입을 만들거나, 동작 설명 주석을 달거나 하는 식으로.

코드로 넘어오면 그 역할이 어디에 있는지 좀 모호해진다는 생각이 들었다. diff를 읽는 사람이 머릿속에서 동작을 시뮬레이션해야 하는데, 그게 생각보다 쉬운 일이 아니니까.

👉🏻 /demo가 흥미로웠던 건, 검증 도구라기보다 커뮤니케이션 도구에 가깝다는 점이었다. 동작이 맞다는 걸 증명하기보다 그 맥락을 같이 보여주는 방향인 것 같았다.

> 💡 **여기서 드는 질문?**
> 에이전트가 UI를 조작할 때 "어떤 흐름을 확인해야 하는가"는 아직 사람이 말해줘야 한다. 그 판단을 어떻게 넘겨주는 게 제일 자연스러울까?

## 3️⃣ GitHub Actions 연동 부분

문서에서 GitHub Actions 연동도 언급되어 있었다. PR마다 자동으로 데모가 생성된다면 리뷰어 입장에서는 시나리오를 직접 짤 필요 없이 영상으로 바로 확인할 수 있는 셈이다.

공부한 내용 기준으로는 리뷰 단계에서 체크아웃 없이도 변경된 동작을 확인할 수 있다는 점이 핵심인 것 같다. 리뷰 비용이 낮아지는 방향이니까.

## ⭐️ 마지막으로, 코드 리뷰를 공부하며 느낀 것

정리해보니 /demo는 테스트 결과를 보강하는 도구라기보다, 변경사항을 설명하는 비용을 낮추는 도구에 가까운 것 같다. "코드가 돌아간다"와 "이 코드가 어떻게 돌아가는지 보여준다"는 결이 다른 일이라는 게, 이번 공부에서 남은 인상이다.
