GitHub 블로그에서 Copilot에 새 기능이 추가됐다는 글을 읽었다. 이름은 캔버스(Canvas)고, 자연어로 설명하면 AI가 실시간으로 작동하는 인터페이스를 만들어준다는 개념이었다. 처음엔 채팅에 뭔가 추가된 수준으로 봤는데, 조금 읽어보니 방향이 좀 달랐다.

관련 글이 두 편이었다. 하나는 입문자 대상 튜토리얼이고, 다른 하나는 "채팅이 왜 틀린 UI인가"라는 제목의 배경 설명이었다. 그 제목이 직설적이어서 따라 읽게 됐다.

## 1️⃣ 이게 뭐냐?

GitHub Copilot에 `/create-canvas`라는 명령이 추가됐다. 사용법은 단순한 편이다. 세 가지를 자연어로 설명하면 된다 — 어떤 워크플로우를 지원하는지, 사용자가 뭘 할 수 있는지, 에이전트가 뭘 할 수 있는지.

그러면 Copilot이 실시간으로 작동하는 커스텀 인터페이스를 만들어준다. 문서에서 나온 예시들은 칸반 보드, 릴리즈 노트 트래커, 이슈 트리아지 보드, 체크리스트 같은 것들이었다. 단순한 UI가 아니라 버튼을 누르면 AI가 즉시 반응하고 그 결과가 같은 화면 안에 바로 반영되는 구조라고 했다.

이걸 문서에서 "양방향(bidirectional)" 상호작용이라고 표현하고 있었는데, 기존 채팅의 "질문 → 텍스트 응답" 흐름과는 다르다는 걸 강조하는 것 같았다. 대화가 아니라 상태를 공유하는 인터페이스에 가깝다는 느낌이었다.

생성된 캔버스는 extension으로 저장해서 팀 전체가 재사용할 수도 있다고 한다.

## 2️⃣ 내가 든 생각

디자이너 관점에서 흥미로웠던 건, 이 기능의 방향이 기존 도구들과 좀 다른 것 같다는 점이었다.

보통은 도구가 먼저 있고, 워크플로우를 거기에 맞춰가는 식이다. Jira가 있으면 Jira 방식으로, GitHub Projects가 있으면 그 방식으로. 캔버스는 그 순서를 뒤집는 것 같다 — 원하는 워크플로우를 먼저 설명하면 거기에 맞는 UI가 생성되는 식이다.

👉🏻 자연어로 인터페이스를 정의한다는 개념 자체가 흥미로웠다. 와이어프레임이나 스펙 문서 대신, 대화로 레이아웃을 기술하는 것에 가까운 흐름이랄까.

생성된 캔버스를 컴포넌트처럼 저장해 재사용한다는 부분도 눈에 띄었다. "이 팀이 매주 쓰는 릴리즈 노트 캔버스" 같은 식으로, 반복적인 워크플로우를 한 번 만들어두는 형태다. 매번 새 채팅을 열고 같은 설명을 다시 하는 것보다 효율적이겠다는 생각이 들었다.

> 💡 **여기서 드는 질문**: 자연어로 UI를 정의한다는 건, 내가 원하는 걸 명확히 언어화할 수 있어야 비로소 작동하는 방식이 아닐까. "뭔가 필요한데 정확히 뭔지 모르는" 상황에선 오히려 시작이 어려울 수도 있겠다는 생각이 들었다.

## 3️⃣ 앞으로 어떻게 쓸까?

공부한 내용 기준으로는, 반복적으로 쓰는 워크플로우에 가장 잘 맞을 것 같다는 인상이었다. 한 번만 쓰는 작업에 캔버스를 만들 이유는 별로 없겠지만, "이 팀이 매주 하는 작업"이라면 정의해두는 게 의미 있을 것 같다.

디자이너 관점에서 보면, 프로토타이핑에 쓰일 수 있을지도 궁금해졌다. 자연어로 UI를 정의한다는 개념이 사용자 플로우를 빠르게 시각화하는 것과 방향이 비슷해 보이기도 했다. 아직 문서만 본 입장에서는 실제로 어떤지 모르겠지만.

## ⭐️ 마지막으로, 이번 공부에서 남은 생각

정리해보니 캔버스는 "더 나은 채팅"보다는 "채팅이 아닌 다른 것"에 가까운 것 같다. 채팅이 대화가 쌓이는 방식이라면, 캔버스는 상태가 공유되는 인터페이스다 — 그 둘의 차이가 결국 이 기능을 단순한 UX 개선이 아닌 다른 레이어로 읽게 만드는 지점인 것 같다.
