토스 테크 블로그에서 설계기 하나를 읽었다. 망분리 환경, 그러니까 외부 인터넷이 차단된 내부망에서 AI 에이전트를 돌리는 플랫폼을 어떻게 만들었는지에 대한 글이다. 제목 자체가 "실행은 격리하고, 세션은 이어간다"여서 처음부터 핵심 트레이드오프가 뭔지 보였다. 왜 그 선택을 했는지 천천히 따라가봤다.

배경만 정리하면: 망분리 환경에서는 에이전트가 외부 API를 직접 쓸 수 없고, 코드 실행이 내부망 안에서 이뤄져야 한다. 여기에 "AI가 직접 코드를 써서 데이터를 분석한다"는 시나리오를 얹으면 꽤 복잡해진다. 에이전트가 실행하는 코드가 다른 사용자 파일이나 내부 서비스에 접근하면 곤란하니까.

## 1️⃣ 이게 뭐냐?

구조는 세 층으로 나뉜다. Workspace(사용자별 작업 공간) → Agent(업무 지침 + 도구 묶음) → Session(대화). 사용자마다 하나의 Pod(컨테이너)가 뜨고, 그 안에서 여러 Agent가 돌아간다.

실행 격리는 bubblewrap이라는 도구를 썼다. VM처럼 각 환경을 별도로 띄우는 방식이 아니라 Linux namespace를 활용하는 경량 방식을 선택했다. VM을 고르면 이미지 관리나 볼륨 연결 부담이 커진다는 이유였다. 완벽한 격리는 아니지만, "에이전트가 다른 사람 파일에 접근하는 것"을 막는 목적에는 충분하다고 판단한 것 같다.

인증 정보는 에이전트에게 직접 주지 않는다. 환경변수 대신 프록시가 요청 시점에 실제 키를 주입하는 방식을 택했다. 에이전트가 키를 갖고 있으면 로그나 출력에서 노출될 수 있다는 이유였다.

## 2️⃣ 내가 든 생각

가장 흥미로웠던 건 "세션은 이어간다"는 부분이었다. 실행은 격리되어 있는데, 대화는 이어져야 한다. "지난달이랑 같은 기준으로 이번 달 데이터도 비교해줘"라는 요청에서, 이전 세션의 코드 파일(`compare.py` 같은)을 그대로 쓸 수 있어야 하는 상황이다.

해결책은 영속 볼륨(PV)이었다. 파일과 세션 상태를 Pod와 분리해서 저장하면, Pod가 바뀌어도 이전 작업을 이어갈 수 있다. 그런데 여기서 트레이드오프가 하나 나온다 — 여러 세션이 같은 파일을 동시에 수정하면 충돌 가능성이 있다는 것. 글에서는 이걸 열린 문제로 명시했다.

👉🏻 한계를 솔직하게 적은 게 인상적이었다. 쓰기 허용된 폴더 안의 잘못된 수정은 막지 못한다고, 중간 작업 재시작이나 파일 롤백은 지원하지 않는다고. "우리가 해결한 것"과 "아직 안 푼 것"의 경계가 뚜렷했다.

> 💡 **여기서 든 질문:** 격리와 연속성의 경계를 어디에 그을지는 결국 "무엇을 더 보호하려는가"의 문제인 것 같은데, 이걸 명시적으로 정의해두지 않으면 나중에 경계가 흐려지지 않을까?

## 3️⃣ 공부하면서 든 맥락

디자이너 입장에서 이 글이 흥미로웠던 이유는 "도구 경계"에 대한 이야기이기 때문이다. 에이전트가 어디까지 접근하고, 어디서 멈춰야 하는지를 시스템 레벨로 강제하는 구조. "지침을 잘 써두면 모델이 알아서 잘 하겠지"가 아니라, 물리적으로 경계를 그어버리는 방식.

공부한 내용 기준으로 보면, 이 설계는 에이전트의 자율성과 시스템 통제 사이에서 선을 그은 사례처럼 읽혔다. 모델이 "할 수 있는 것"을 도구 목록이 아니라 실행 환경 자체로 제한한다는 발상이 흥미로웠다.

## ⭐️ 마지막으로, 설계기를 공부하며 느낀 점

정리해보니 이 설계기는 에이전트를 효율적으로 돌리는 이야기보다, 에이전트를 어디까지 신뢰할 수 있냐는 이야기에 가까웠다.
