GitHub 블로그에서 Git 저장소 아키텍처를 새로 설계했다는 글이 올라왔다. 에이전트 도구를 조금씩 공부하는 중이라 AI 에이전트가 코드를 많이 커밋하면 저장소 쪽에 어떤 일이 생기는지 궁금했는데, 이 글이 그 질문에 직접 답하고 있었다.

읽어보니 출발점은 단순했다. 에이전트 하나가 아니라 수천 개의 에이전트가 한 저장소에 동시에 push를 날리는 상황을 가정하고 설계를 다시 했다는 거다. AI 에이전트가 늘어날수록 저장소에 가해지는 쓰기 압력도 같이 커지는 거고, 기존 구조로는 그걸 감당하기 어렵다는 얘기였다.

## 1️⃣ 이게 뭐냐?

기존 방식은 브랜치나 태그 같은 레퍼런스 정보를 단일 blob으로 관리했는데, 여러 쓰기가 동시에 들어오면 충돌이 생기는 구조였다고 한다. 혼자 작업하는 저장소라면 문제없지만, 에이전트들이 동시에 push를 보내기 시작하면 얘기가 달라지는 거다.

새 아키텍처의 중심에는 **Ref-CAS**라는 서비스가 있다. 레퍼런스를 하나씩 compare-and-swap 방식으로 처리한다. "지금 이 버전이 맞으면 바꿔, 아니면 거절해"라는 식이다. 덕분에 여러 쓰기가 동시에 들어와도 각자 독립적으로 처리할 수 있다.

Git 객체(pack, 인덱스)는 Azure Blob Storage에 올라간다. 로컬 디스크는 캐시 역할만 하고, 언제든 다시 만들 수 있는 임시 공간에 가깝다. 읽기와 쓰기를 담당하는 virtual replica는 필요할 때 생성되는 일회성 컴퓨트 노드에 가까운 개념이다.

pack을 합치고 오래된 객체를 정리하는 compaction 작업은 별도 노드에서 돌아간다. 서빙 노드와 분리해서 운영하는 구조인데, 한 작업이 다른 작업에 영향을 주지 않게 하려는 거라고 이해했다.

## 2️⃣ 내가 든 생각

"인프라 얘기니까 나랑은 거리가 멀겠다"고 생각하면서 읽기 시작했다. 근데 Ref-CAS 설명을 보다가 프론트엔드에서 익숙한 패턴이랑 겹치는 게 있었다.

버전을 먼저 비교하고, 변경이 없으면 아무것도 안 하는 구조. HTTP 헤더에서 `ETag`나 `If-None-Match`로 조건부 요청을 보내는 거랑 발상이 비슷하다는 생각이 들었다. 이 아키텍처에서도 레퍼런스 버전(LSN)이 같으면 추가 작업 없이 그냥 넘어간다. 한쪽은 Git이고 한쪽은 HTTP지만, "변경 없으면 그냥 패스" 패턴은 꽤 보편적인 발상인 것 같다.

👉🏻 쓰기 한 번이 일어나면 CI, 배포 시스템, 다른 에이전트들의 읽기가 연쇄적으로 뒤따른다는 설명이 흥미로웠다. 단순히 쓰기 처리량을 늘리는 문제가 아니라, 그 뒤에 따라오는 읽기 폭발을 어떻게 감당하느냐가 핵심이라는 거다.

디자이너로서 보면, 로드맵에 있는 event streams나 Atomic commit API 같은 아이템이 더 눈에 들어왔다. 여러 파일을 한 번에 커밋하거나 저장소 변경을 실시간으로 구독할 수 있게 되면, 디자인 에셋이나 토큰 관리 방식에도 연결될 수 있겠다는 생각이 들었다.

> 💡 **여기서 드는 질문?**
> compare-and-swap으로 "거절된" 쓰기는 어떻게 재시도될까? 에이전트 쪽에서 직접 처리해야 하는 건지, 아니면 Ref-CAS 레이어에서 자동으로 뭔가를 해주는 건지 궁금해졌다.

## ⭐️ 마지막으로, 아키텍처 공부를 하면서 느낀 점

이번 공부 끝에 남은 한 줄은 이거였다 — 쓰기 처리량 문제는 결국 충돌을 어떻게 쪼개느냐의 문제라는 것. Ref-CAS가 하는 일도 그거고, 서빙 노드와 compaction 노드를 나누는 것도 그거다. 프론트엔드에서 상태를 나눌 때도 같은 질문이 나오는 걸 보면, 도구가 달라도 고민하는 방향은 비슷한 것 같다.
