GitHub 블로그에서 Java Champions 3명이 GitHub Copilot을 어떻게 쓰는지 정리한 글을 읽었다. 처음엔 "또 AI 도구 홍보글이겠지" 싶었는데, 읽어보니 자동완성 얘기가 아니었다. 에이전트 기반 워크플로 얘기였고, 세 사람이 공통적으로 비슷한 결론을 갖고 있다는 게 흥미로웠다.

흥미로웠던 건 "어떻게 쓰는가"보다 "어떻게 책임지는가"를 더 많이 이야기한다는 점이었다.

## 1️⃣ 이게 뭐냐?

세 사람 모두 IDE 자동완성 중심이 아니라, 에이전트에게 작업을 맡기고 검증 게이트를 통과하면 다음 단계로 넘어가는 방식을 쓰고 있었다.

각자의 사례를 보면: Vlad는 자기 블로그 글들을 학습시킨 개인 스킬을 만들었다. 생성된 문서가 기계 문장이 아닌 자기 글처럼 나오게 하려는 거였다. Patrick은 수백 장짜리 발표 슬라이드를 다른 포맷으로 마이그레이션할 때 에이전트를 써서 예상보다 훨씬 빠르게 끝냈다. Frank는 Raspberry Pi 프로젝트 버그 수정을 에이전트에게 맡겼는데, 관련 파일 경로 두 개를 넘겨주자 꽤 빠르게 PR이 올라왔다.

패턴이 있었다. "큰 작업을 한 번에 맡기지 않는다"는 것. 작게 나눠 진행하고, 각 단계마다 "완료"를 어떻게 증명할지 미리 정해뒀다.

## 2️⃣ 내가 든 생각

세 글에서 반복되는 표현이 있었다 — "delegate execution, not responsibility". 실행은 맡기되 책임은 위임하지 않는다는 말.

처음엔 당연한 소리처럼 들렸다. 근데 조금 더 읽으니 생각이 달라졌다. Frank가 PR에 "이 수정이 가상 스레드의 목적과 모순되지 않나?"라고 질문할 수 있었던 건, 가상 스레드가 뭔지 알고 있었기 때문이다. 책임을 지려면 오히려 더 잘 알아야 한다는 얘기에 가까웠다.

Vlad의 개인 스킬 방식도 흥미로웠다. 디자이너 관점에서 보면 이건 "AI를 쓰면서도 목소리를 잃지 않으려는" 작업에 가까운 것 같았다. 도구가 일을 해줄수록 일관성은 어디서 오는가, 하는 질문이랑 비슷한 문제처럼 느껴졌다.

👉🏻 Patrick의 검증 게이트 방식 — 테스트 통과, 문서 갱신, TODO 없음, 시각 비교 — "완료"를 증거로 정의한다는 발상이 가장 인상적이었다.

> 💡 **에이전트를 잘 쓰는 핵심은 프롬프트 설계보다 "완료"를 어떻게 정의하느냐에 있는 건 아닐까?**

## 3️⃣ 앞으로 어떻게 쓸까?

공부한 내용 기준으로는, 에이전트 워크플로에서 가장 먼저 해야 할 게 "완료 기준 설정"인 것 같다. 작업을 맡기기 전에 "이게 끝나면 어떤 상태여야 하는가"를 먼저 정해두는 것.

아직 직접 닿아본 적은 없지만, 이 방식을 디자인 작업에도 적용해볼 수 있을지 궁금해졌다. 컴포넌트 문서화나 스펙 작성 같은 작업에서 검증 기준을 먼저 잡아두는 방식. Vlad가 개인 스킬로 문체를 유지한 것처럼, 디자이너가 AI를 쓰면서도 일관성을 지키는 방법이 있을 것 같다는 생각이 들었다.

## ⭐️ 마지막으로, 에이전트 워크플로를 공부하면서

정리해보니 "AI를 잘 쓰는 것"이 결국 "위임을 잘 하는 것"에 가까운 일이었다. 그리고 위임을 잘 하려면 맡기는 대상을 잘 알아야 한다. 세 사람이 보여준 건 AI 활용 팁이라기보다 도메인 이해도의 차이에 더 가까웠다.
