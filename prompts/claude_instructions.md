# 블로그 포스트 자동 생성 작업 (v2)

Jerry의 Jekyll 블로그에 올릴 새 포스트를 **한 편** 생성합니다.
아래 단계를 **순서대로** 실행하세요.

## 🎯 이번 작업의 정체성

**"Jerry가 최근 공식 발표를 읽고 공부한 뒤 정리한 학습 노트"**

- ❌ 분석글, 파헤치기, 심층 해설 (X)
- ✅ 공부한 뒤 "나는 이렇게 이해했다"를 담담히 정리 (O)

---

## ⚠️ 절대 규칙

1. **본문 100% 한국어** (코드/함수명/제품명은 영문 OK)
2. **원문을 번역하지 말 것** → 공부한 뒤 **내 언어로 재구성**
3. **1500자 내외** (공백 제외, ±300자)
4. **단정·호들갑·권위 인용 금지** — `style_guide.md`의 블랙리스트 엄수
5. **Jerry가 실제로 쓸 문장만** 사용
6. **"Generated by Claude" 같은 꼬리말 절대 금지**

## Step 1: 후보 확인

`scripts/candidates.json` 읽기.

```json
{
  "category": {
    "id": "design-tools" | "frontend" | "dev-tools",
    "display_name": "Design" | "Frontend" | "DevTools",
    "korean_label": "디자인 도구" | "프론트엔드 프레임워크" | "개발자 도구",
    "color_start": "#...",
    "color_end": "#..."
  },
  "next_category_index": 0,
  "candidates": [
    { "title": "...", "url": "...", "summary": "...", "source": "...", "published": "...", ... }
  ]
}
```

**후보가 비어있으면** → "후보 없음. 이번 턴 스킵." 출력하고 **여기서 종료**. 아무 파일도 만들지 마세요.

---

## Step 2: 원문 선택

`candidates`의 **상위 5개**를 훑어보고, 아래 우선순위로 고르기:

1. **공식 발표/릴리스** (React 18→19 같은 업데이트, Figma Dev Mode MCP 등)
2. **새로운 베타 기능** (Cursor, Claude Skills, Tailwind v4 등)
3. **큰 정책/구조 변화** (배포 방식 변경, 큰 API 변화)

선택한 후보에서 아래 값 기억:
- `title`, `url`, `summary`, `source`

**❗ 피할 것**: 자잘한 버그 수정, 루틴한 보안 패치는 스킵하고 다른 후보 선택.

---

## Step 3: WebFetch로 원문 꼼꼼히 읽기

`summary`만 가지고 쓰면 피상적인 글 나옴. **반드시 WebFetch** 사용:

```
WebFetch(url=선택한 후보의 url, prompt="이 발표의 핵심, 구체적인 기능/API, 이전과 달라진 점을 추출해줘")
```

추출할 것:
- **뭐가 새로 나왔나?** (기능 이름, 핵심 변경점)
- **이전과 뭐가 다른가?** (변화의 방향)
- **어떤 구체 예시가 있나?** (API 이름, 사용 시나리오)
- **디자이너/프론트 학습자 관점에서 뭐가 의미 있나?**

> ⚠️ WebFetch 실패 시: `summary`만 가지고 작성. **추측 금지**. 확실한 정보만 다루고, "자세한 건 원문 참고"라고 남기기.

## Step 5: 한국어 학습 노트 작성

### 길이
**1500자 내외** (공백 제외, ±300자 허용)

### 구조 (공식 발표 학습 노트)

```markdown
## 도입부 (2~3 문단)
"[회사] 블로그에서 [기능] 발표가 있었다."
"읽어보니 [흥미로운 포인트]가 궁금해져서 공부해봤다."
→ 구체적인 진입점, 호들갑 없이 담담하게

## **1️⃣ 이게 뭐냐?** (3~4 문단)
발표의 핵심을 내 언어로 정리
코드/API 예시 있으면 한두 개만
기능 나열하지 말고 핵심 개념 중심으로

## **2️⃣ 내가 든 생각** (3~4 문단)
디자이너/학습자 관점에서의 관찰
"~이 흥미로웠다", "~가 궁금해졌다"
👉🏻 핵심 포인트 표시 (1회)

> 💡 **여기서 드는 질문?**
(이 질문이 다음 섹션으로 자연스럽게 이어지게)

## **3️⃣ 앞으로 어떻게 쓸까?** (2~3 문단, 선택)
실제로 써볼 만한 맥락
"써봐야 알겠지만" 톤
(쓸 말이 없으면 생략 가능)

## **⭐️ 마지막으로, [관점]에서 공부하며 느낀 점**
```
이번에 공부하면서 [주제]에서 중요한 건
[표면적 특징]이 아니라
**[더 본질적인 감각]**이라는 생각이 들었다.
```

---

> 참고 원문: [원문 제목](원문 URL)
```

### 메타 정보 결정

- **title**: 한글 제목, **"공부 정리"/"정리한 것"/"훑어본 뒤"** 같은 학습 톤
  - 예: `Claude Skills 공부 정리 | 이게 결국 뭘 바꾸는 걸까`
  - 예: `React 19 Actions 훑어보면서 든 생각`
  - 예: `Figma Dev Mode MCP 써보려고 문서 정리한 것`
  - ❌ "파헤치기", "완벽 가이드", "심층 분석" 금지

- **description**: 한 줄 요약 (80자 이내). 담백하게.

- **slug**: 영문 소문자+하이픈, 60자 이내. 예: `claude-skills-study-note`

- **categories**: `candidates.json`의 `category.display_name` 그대로 사용
  - design-tools → `[Design]`
  - frontend → `[Frontend]`
  - dev-tools → `[DevTools]`
  - ⚠️ 하이픈 없는 카테고리명 필수 (Chirpy 호환성)

- **tags**: 영문 소문자 3~5개 (예: `[react, hooks, react-19]`)

## Step 6: 썸네일 선택 (기존 PNG 재사용)

`assets/img/thumbnail/`에 **이미 있는 주제별 PNG** 중에서 하나를 고른다.
**새로 생성하지 말 것** — `make_thumbnail.py` 호출 금지.

**매칭 규칙** (후보의 `tags` / `title` 기반):

| 주제 키워드 | 썸네일 파일 |
|---|---|
| `react`, `hooks`, `jsx`, `react-19` 등 React 계열 | `react.png` |
| `next`, `next-js`, `nextjs`, `vercel` | `next-js.png` |
| `javascript`, `js`, `ecmascript` | `javascript.png` |
| `typescript`, `ts` | `typescript.png` |
| **그 외 전부** (Claude, Figma, Framer, Anthropic, DevTools 등) | `self-study.png` |

매칭되는 키워드가 없으면 반드시 **`self-study.png`**를 기본값으로 사용.

## Step 7: MD 파일 저장

경로: `_posts/YYYY-MM-DD-<slug>.md` (한국 시간)

```markdown
---
title: "<한글 title>"
description: "<한 줄 요약>"
date: YYYY-MM-DD HH:MM:SS +0900
categories: [<카테고리>]
tags: [<tag1>, <tag2>, <tag3>]
image:
  path: /assets/img/thumbnail/<Step 6에서 고른 파일명>.png
  alt: "<한글 title>"
---

<본문>

---

> 참고 원문: [<원문 제목>](<원문 URL>)
```

**⚠️ 필수 체크**:
- 프론트매터 모든 문자열 값을 **쌍따옴표**로 감싸기
- title에 `|` 있으면 **반드시** 쌍따옴표
- `categories`에 **하이픈 없는 단어만** (예: `[Design]`, `[Frontend]`, `[DevTools]`)
- `image.path`는 `assets/img/thumbnail/`에 **실제로 존재하는** 파일이어야 함 (Step 6 매칭표 기준)
- date는 한국시간 `+0900`

## Step 8: 자기 검증 (중요!)

저장 전에 **반드시 본문을 다시 읽고** 체크:

- [ ] "~이다" 단정이 5번 이상인가? → 줄이기
- [ ] "완전히/혁명적/반드시" 있나? → 삭제
- [ ] 수치/기관 인용 있나? → 삭제
- [ ] "여러분" 호칭 있나? → 삭제
- [ ] 결론이 거창한 선언인가? → "~에 가까웠다"로 변경
- [ ] 1500자 ±300자 범위 안인가? → 잘라내기
- [ ] Jerry가 실제로 쓸 만한 문장들인가? → 어색한 것 교체
- [ ] 원문 번역한 느낌 드는가? → 내 언어로 재작성

**위 항목 중 하나라도 ❌이면 수정 후 저장.**
