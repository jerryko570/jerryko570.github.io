# 블로그 포스트 자동 생성 작업 (v3)

Jerry의 Jekyll 블로그에 올릴 새 포스트를 **한 편** 생성합니다.
아래 단계를 **순서대로** 실행하세요.

## 🎯 이번 작업의 정체성

**"Jerry가 최근 공식 발표를 읽고 공부한 뒤 정리한 학습 노트"**

- ❌ 분석글, 파헤치기, 심층 해설
- ✅ 공부한 뒤 "나는 이렇게 이해했다"를 담담히 정리

---

## ⚠️ 절대 규칙

1. **본문 100% 한국어** (코드/함수명/제품명은 영문 OK)
2. **원문을 번역하지 말 것** → 공부한 뒤 **내 언어로 재구성**
3. **1500자 내외** (공백 제외, ±300자 허용)
4. **단정·호들갑·권위 인용 금지** — `prompts/style_guide.md`의 블랙리스트 엄수
5. **Jerry가 실제로 쓸 문장만** 사용
6. **"Generated by Claude" 같은 꼬리말 절대 금지**

## Step 1: 후보 확인

`scripts/candidates.json`을 읽습니다.

```json
{
  "category": {
    "id": "design-tools" | "design-craft" | "frontend" | "dev-tools",
    "display_name": "Design" | "DesignCraft" | "Frontend" | "DevTools",
    "korean_label": "디자인 도구" | "프로덕트 디자인" | "프론트엔드 프레임워크" | "개발자 도구",
    "color_start": "#...",
    "color_end": "#..."
  },
  "next_category_index": 0,
  "candidates": [
    { "title": "...", "url": "...", "summary": "...", "source": "...", "published": "...", ... }
  ]
}
```

**파일이 없거나 `candidates`가 비어있으면** → "후보 없음. 이번 턴 스킵." 출력하고 **여기서 종료**. 아무 파일도 만들지 마세요.

---

## Step 2: 원문 선택

`candidates`의 **상위 5개**를 훑고 아래 우선순위로 한 편 고릅니다.

1. **공식 발표 / 릴리스** (React 18→19 같은 업데이트, Figma Dev Mode MCP 등)
2. **새 베타 기능** (Cursor, Claude Skills, Tailwind v4 등)
3. **큰 정책·구조 변화** (배포 방식 변경, 큰 API 변경)
4. **DesignCraft 카테고리**의 경우: 의사결정 과정·실패 경험·디자인 시스템 케이스가 담긴 글 우선

선택한 후보의 `title`, `url`, `summary`, `source`를 기억해 두세요.

**❗ 피할 것**: 자잘한 버그 수정·루틴한 보안 패치는 스킵, 다음 후보로.

## Step 3: WebFetch로 원문 꼼꼼히 읽기

`summary`만으로 쓰면 피상적인 글이 나옵니다. **반드시 WebFetch** 사용:

```
WebFetch(
  url=선택한 후보의 url,
  prompt="이 발표의 핵심, 구체적인 기능/API, 이전과 달라진 점을 추출해줘"
)
```

추출할 것:

- **뭐가 새로 나왔나?** (기능 이름, 핵심 변경점)
- **이전과 뭐가 다른가?** (변화의 방향)
- **어떤 구체 예시가 있나?** (API 이름, 사용 시나리오)
- **디자이너/프론트 학습자 관점에서 뭐가 의미 있나?**

> 한국어 원문(DesignCraft 카테고리 등)일 때도 그대로 번역·요약하지 말고, 의사결정 흐름과 핵심 통찰을 발췌해 학습 노트로 재구성합니다.

> ⚠️ WebFetch 실패 시: `summary`만 가지고 작성, **추측 금지**, 확실한 정보만 다루고 "자세한 건 원문 참고"라고 남기기.

## Step 5: 한국어 학습 노트 작성

### 길이
**1500자 내외** (공백 제외, ±300자 허용)

### 구조

```markdown
## 도입부 (2~3 문단)
"[회사] 블로그에서 [기능] 발표가 있었다."
"읽어보니 [흥미로운 포인트]가 궁금해져서 공부해봤다."
→ 구체적인 진입점, 호들갑 없이 담담하게

## 1️⃣ 이게 뭐냐? (3~4 문단)
발표의 핵심을 내 언어로 정리.
코드/API 예시는 한두 개만.
기능 나열보다 핵심 개념 중심으로.

## 2️⃣ 내가 든 생각 (3~4 문단)
디자이너/학습자 관점의 관찰.
"~이 흥미로웠다", "~가 궁금해졌다"
👉🏻 핵심 포인트 표시 (1회)

> 💡 **여기서 드는 질문?**
(이 질문이 다음 섹션으로 자연스럽게 이어지도록)

## 3️⃣ 앞으로 어떻게 쓸까? (2~3 문단, 선택)
실제로 써볼 만한 맥락.
"써봐야 알겠지만" 톤.
(쓸 말 없으면 생략)

## ⭐️ 마지막으로, [관점]에서 공부하며 느낀 점

이번에 공부하면서 [주제]에서 중요한 건
[표면적 특징]이 아니라
**[더 본질적인 감각]**이라는 생각이 들었다.

---

> 참고 원문: [원문 제목](원문 URL)
```

### 메타 정보 결정

- **title**: 한글 제목, **"공부 정리"·"정리한 것"·"훑어본 뒤"** 같은 학습 톤
  - 예: `Claude Skills 공부 정리 | 이게 결국 뭘 바꾸는 걸까`
  - 예: `React 19 Actions 훑어보면서 든 생각`
  - 예: `토스의 큰 글씨 모드 케이스 정리`
  - ❌ "파헤치기", "완벽 가이드", "심층 분석"

- **description**: 한 줄 요약, 80자 이내, 담백하게.

- **slug**: 영문 소문자+하이픈, 60자 이내. 예: `claude-skills-study-note`

- **categories**: `candidates.json`의 `category.display_name` 그대로 사용
  - `design-tools` → `[Design]`
  - `design-craft` → `[DesignCraft]`
  - `frontend` → `[Frontend]`
  - `dev-tools` → `[DevTools]`
  - ⚠️ **하이픈 없는 단어만** (Chirpy 호환성)

- **tags**: 영문 소문자 3~5개. 예: `[react, hooks, react-19]`

## Step 6: 썸네일 자동 생성

`scripts/make_thumbnail.py`를 호출해서 글 전용 썸네일을 만든다.

```bash
python scripts/make_thumbnail.py \
  "<한글 title>" \
  "<category.display_name>" \
  "<category.color_start>" \
  "<category.color_end>" \
  "assets/img/thumbnail/<slug>.png" \
  "<주요 영문 키워드 하나, 예: webflow>"
```

스크립트가 tags/title에서 영문 라벨을 자동 추출해 컬러 카드를 만든다.
프론트매터의 `image.path`는 `/assets/img/thumbnail/<slug>.png` 로 적는다.

> 기존 React/Next/JS/TS PNG는 더 이상 사용하지 않는다. 모든 자동 생성 글은 슬러그명으로 새 PNG를 만든다.

> Jerry 지시(2026-04-22): 자동 생성 그라데이션 썸네일보다 기존 주제별 일러스트 PNG가 블로그 톤에 맞는다.

## Step 7: MD 파일 저장

경로: `_posts/YYYY-MM-DD-<slug>.md` (한국시간 기준)

```markdown
---
title: "<한글 title>"
description: "<한 줄 요약>"
date: YYYY-MM-DD HH:MM:SS +0900
categories: [<카테고리>]
tags: [<tag1>, <tag2>, <tag3>]
image:
  path: /assets/img/thumbnail/<Step 6에서 고른 파일명>.png
  alt: "<한글 title>"
---

<본문>

---

> 참고 원문: [<원문 제목>](<원문 URL>)
```

**⚠️ 필수 체크**:

- 프론트매터의 모든 문자열 값을 **쌍따옴표**로 감싸기
- title에 `|`가 있으면 **반드시** 쌍따옴표
- `categories`는 **하이픈 없는 단어** (`[Design]`, `[DesignCraft]`, `[Frontend]`, `[DevTools]`)
- `image.path`는 `assets/img/thumbnail/`에 **실제로 존재하는** 파일
- date는 한국시간 `+0900`

## Step 8: 자기 검증

저장 전 **본문을 다시 읽고** 체크하세요.

- [ ] "~이다" 단정이 5번 이상인가? → 줄이기
- [ ] "완전히/혁명적/반드시" 있나? → 삭제
- [ ] 수치/기관 인용 있나? → 삭제
- [ ] "여러분" 호칭 있나? → 삭제
- [ ] 결론이 거창한 선언인가? → "~에 가까웠다"로 변경
- [ ] 1500자 ±300자 범위 안인가? → 조정
- [ ] Jerry가 실제로 쓸 만한 문장인가? → 어색한 것 교체
- [ ] 원문 번역한 느낌인가? → 내 언어로 재작성

**하나라도 ❌이면 수정 후 저장.**

## Step 9: 상태 업데이트 (생략 금지)

포스트 저장과 썸네일 지정까지 끝났다면, 아래 명령을 **반드시** 실행하세요.
빠뜨리면 다음 회차에 같은 글이 또 발행됩니다.

```bash
python scripts/update_state.py <<'JSON'
{
  "category_index": <candidates.json의 next_category_index 값>,
  "category_id": "<candidates.json의 category.id 값>",
  "source_url": "<선택한 후보의 url>",
  "post_title": "<생성한 한글 포스트 title>"
}
JSON
```

성공 시 `✅ state.json 업데이트 완료 (...)` 메시지가 출력됩니다. 메시지를 못 봤거나 종료 코드가 0이 아니면 **다시 실행**하세요.
